## T01 路径检测：四方向无阻挡 / 贴边出界

- **目的**：验证 `Board.can_fly` 在箭头前方没有别的线段时返回 `True`，包括箭头贴在棋盘边上、下一步就出界的情况。
- **用例**：`tests/test_path.py::test_four_directions_clear`、`test_edge_flies_out[0-0-U / 4-4-D / 0-4-L / 4-0-R]`
- **步骤**：构造 5×5 空棋盘，放一支贴在边缘、朝向盘外的箭，调用 `can_fly`。
- **预期**：四个方向、四条边，全部返回 `True`。
- **实际**：5 个用例全过。
- **结论**：出界判定与 `in_bounds` 拼接正确，没有数组越界。

## T02 路径检测：被线段挡住

- **目的**：验证箭头射线上有别的线段时返回 `False`，且判断会穿透整条射线而不只看下一格。
- **用例**：`test_blocked_four_directions[head0-U / head1-D / head2-L / head3-R]`、`test_segment_body_blocks`
- **步骤**：
  1. 在箭头正前方 2 格处放一支「自己朝外能飞」的箭，检查原箭被挡、阻挡者能飞；
  2. 放一条竖折线，让它的一段身体落在横箭的射线上，检查横箭被挡。
- **预期**：被挡方 `False`，阻挡方 `True`（说明挡住的判定来自别人的**身体**，不是别人也飞不出去）。
- **实际**：5 个用例全过。
- **结论**：射线是从箭头下一格一直扫到出界，正确。

## T03 折线箭沿自身轨迹滑出，而不是横向扫过

- **目的**：本项目最核心的一条规则 —— 线段拐弯时，身体只沿自己的格子前进，不会横扫旁边的格子。
- **用例**：`test_bent_flows_along_own_path`、`test_bent_head_ray_blocked`
- **步骤**：构造 L 形箭 `(2,0)→(2,1)→(1,1)`，箭头朝上：
  1. 在尾格旁边 `(1,0)` 放一支箭 —— 它不在 L 形的滑出路径上；
  2. 把箭改放到 `(0,1)` —— 正好压在箭头射线上。
- **预期**：情形 1 两支都能飞；情形 2 L 形被挡。
- **实际**：两个用例全过。
- **结论**：判定只看箭头那一条射线，身体不参与碰撞。

## T04 关卡生成器：造型遮罩 + 可通关性 + 填充率

- **目的**：确认 8 种造型的遮罩合法且四连通；生成出来的每一关都真的可通关；盘面密度对齐参考游戏。
- **用例**：`tests/test_generator.py`（共 17 个）
- **步骤**：
  1. 对 rect / round / diamond / heart / triangle / cross / hourglass / ring 逐个取 13×13 遮罩，检查格子都在棋盘内、且四连通；
  2. 生成 4 种造型的关卡，逐条检查：每支箭 ≥2 格、方向字符合法、格子全在遮罩内、相邻格曼哈顿距离为 1；
  3. 用 `verify_solution()` 拿真棋盘按 `solution` 模拟点一遍；
  4. 独立用 `solver.solve()` 再解一遍做交叉验证；
  5. 检查填充率 ≥ 0.85。
- **预期**：全部满足。
- **实际**：全过。当前 12 关的实际填充率为 0.94 ~ 1.00（`tools/generate_levels.py --stats` 输出）。
- **结论**：逆向构造法有效；「生成器说可解」和「求解器独立求解」两条路径互相印证。

> **附：填充率调优过程。** 最初线段短、直行多，盘面很稀疏（第 3 关只铺到 0.53），
> 与参考录屏「密密麻麻铺满」的观感差距明显。把 `straight_bias` 从 0.62 降到 0.24、
> `max_piece` 提到 26 之后，长箭绕来绕去反而把棋盘铺得更满，同时因为拐弯频繁，
> 观感上仍然是「一堆短折线缠在一起」而不是几根长横条。
> 这一版的密度达标了，却把玩法弄丢了（盘面没有阻挡），见 T08。

- **预期**：如上。

## T07 窗口尺寸收敛与缩放响应

- **目的**：修掉「窗口无法调整大小、也拖不动」的缺陷，并防止回归。
  成因是窗口默认高 1000，比桌面（非 DPI 感知进程看到的逻辑尺寸）还高，
  Windows 把窗口垂直居中后标题栏和底边双双跑到屏幕外（实测 `top = −81`、
  `bottom = 958`），用户抓不到边框也抓不到标题栏。
- **用例**：`tests/test_window.py`（共 12 个）
- **步骤**：
  1. 纯函数层：`usable_window_cap()` 是否留出标题栏 / 任务栏余量、
     `fit_to_screen()` 是否等比收敛且从不放大、任意桌面尺寸下结果都放得下；
  2. 环境识别：dummy 驱动会谎报 1024×768，`desktop_size()` 必须返回 `None`，
     否则截图与测试环境的窗口会被误缩小；
  3. 接入 `Game`：monkeypatch 成 1440×900 的桌面，断言初始窗口与最小尺寸都在
     `usable_window_cap()` 之内；dummy 环境下断言尺寸仍为默认值（截图不受影响）；
  4. 缩放响应：`_resize()` 后窗口尺寸、`view_scale`、`view_rect` 都跟着更新；
     拖到下限以下会被夹到 `min_window`，且不会反复重建窗口；
  5. 尺寸与当前 surface 一致时不调用 `set_mode`（拖拽期间不重建窗口）；
  6. 缩放后点击映射仍然精准（画布坐标 → 窗口坐标 → 反算命中格）。
- **预期**：全部通过。
- **实际**：12 个用例全过；另用真实窗口 + Win32 `MoveWindow` 做了一次端到端
  回归（窗口外框落在 `top = 39`、`bottom = 838`，上下边框均回到屏幕内）。
- **结论**：窗口可正常拖拽缩放；无窗口环境（截图 / CI）行为不变。

## T08 关卡阻挡与难度曲线（含求解器重写）

- **目的**：修掉「关卡互相没有阻挡、无脑乱点必通关」的缺陷，并防止回归。
  成因是生成器的第二条放置约束（身体不许压在已放好箭的射线上），它和第一条
  （自己的射线上不能有已放好的箭）合起来等价于对任意两支箭 `射线(a) ∩ 身体(b) = ∅`，
  于是开局每一支箭都能直接飞出去，**阻挡在数学上不可能出现**。
- **用例**：`tests/test_blocking.py`（共 29 个），另改动 `test_game_flow.py` 中
  一条把该 bug 当成预期行为的旧用例。
- **步骤**：
  1. 诊断：对 12 关逐关统计开局可飞箭数、被挡箭比例、平均每支箭被几支挡住 ——
     改之前量到的是**全部 100% 可飞、0% 被挡**；
  2. 删掉第二条约束后，用「箭头前方空走廊长度」的偏好度 `ray_pref` 当难度旋钮，
     扫参对照填充率：`ray_pref` 0 → 1 时开局可飞 99% → 22%、被挡 0.9% → 78%，
     填充率反而 0.924 → 0.965；
  3. 为每个关卡配 `ray_pref` 与「开局可飞上限」，重生成 12 关，检查难度逐关递减；
  4. 断言正式关卡「必须有能点的，也必须有点不动的」，且被挡比例 ≥ 0.25；
  5. 求解器：用「一条 A 被 B 挡、B 被 C 挡的链」断言只能从 C 开始（`solve` 返回
     `[2, 1, 0]`）；用「两支互相封死」断言返回 `None`；断言求解器算出的
     「入度为 0」集合与棋盘自己的可飞集合完全一致；对 12 关全量求解并真的执行一遍；
     对最大的关卡断言求解耗时 < 0.5 s；
  6. 生成器：断言 `ray_pref=1` 时被挡比例 ≥ 0.5、`ray_pref=0` 时 ≤ 0.2（旋钮真的起作用）；
     断言重阻挡不会生成死局（`verify_solution` 与 `solve` 双通过）。
- **预期**：全部通过。
- **实际**：29 个用例全过。12 关的「开局可飞」比例为
  67% → 58% → 50% → 50% → 42% → 31% → 28% → 21% → 20% → 15% → 14% → 11%，
  逐关严格不回升；被挡比例 33% ~ 89%，平均每支箭被 1.73 支箭挡住；
  填充率 0.94 ~ 1.00。最大的一关求解耗时 < 0.01 s。
- **结论**：关卡现在必须排出先后顺序才能通关；提示与 AI 自动求解在有阻挡的盘面上
  也能毫秒级给出正确解。

> **附：顺带修掉的求解器缺陷。** 原来的求解器是「深度优先搜索 + 失败局面记忆化」，
> 在无阻挡的盘面上看着没问题（随便一条路都通），但那是假象：每步平均四五支可飞、
> 深度一二十层，搜索树指数爆炸，60 万节点的上限瞬间打满，于是**有解的关卡被判成无解**，
> 提示与自动求解直接失效。改成「谁挡谁」建图 + Kahn 拓扑排序后，O(n²) 精确判定：
> 图无环则任意拓扑序都是解，图有环（互相封死）才真的无解。

## T09 棋盘缩放与拖动（含「点 vs 拖」判定）

- **目的**：修掉「棋盘能放大缩小，但拖不动」的缺陷，并防止回归。
  成因是 `_compute_geometry()` 只按缩放算出居中坐标，没有任何平移量，而放到最大时
  **12 关每一关都横向溢出可视区**（131~171 像素，其中 5 关纵向也溢出 158~252 像素），
  溢出的部分用户看不到也够不着。修的时候还得同时解决「拖棋盘」与「点击线段让它飞」的
  冲突 —— 正式关卡填充率 0.94~1.00，若按下即点，想拖棋盘就一定先点飞一支箭。
- **用例**：`tests/test_pan.py`（共 24 个），另改动 `test_game_flow.py` 的点击合成方式
  （从只发 `MOUSEBUTTONDOWN` 改成成对发「按下 + 抬起」）。
- **步骤**：
  1. 前提：断言默认缩放下 `_can_drag()` 为假（棋盘本来放得下），放到最大后为真且
     `board_pixel_w > 可视区宽`；缩小到 `ZOOM_MIN` 时位置锁死在居中、`pan_by()` 返回 False；
  2. 拖动：从线段格心按住拖 (60, 40)，断言棋盘精确平移 (60, 40)、线段一支不少、红心不扣、
     无飞行动画（拖动绝不能误触发点击）；中键 / 右键拖动同样生效；
  3. 点 vs 拖：只按下不松手不触发；按下后原样松手正常飞出；手抖 `DRAG_THRESHOLD - 1`
     像素仍算点击；位移超过阈值则这次点击作废，不会误飞；
  4. 边界：往 ±6000 像素猛拖，断言棋盘始终落在夹取区间内、可视区里永远留着能点的格子
     （不会被拖出屏幕找不回来）；拖到边界后往回拖 10 像素，棋盘必须立刻跟 10 像素
     （`pan` 已写回夹取值，不会「粘住空转」）；
  5. 缩放的锚点：锚在指针上缩放时，指针底下那个棋盘位置在缩放前后偏差 < 0.005，
     且明显优于「按中心缩放」的偏差；滚轮上下滚动同样锚定指针，并夹在缩放区间内；
  6. 复位：滚轮缩回 100%、`0` 键复位、缩小到装得下、换关、重开时 `pan` 都归零、棋盘
     回到正中；方向键平移与 `+` `-` 缩放按固定步长生效；
  7. 拖动后再做格心命中测试（画布坐标 → 命中格）仍然精准。
- **预期**：全部通过。
- **实际**：24 个用例全过，当轮全量 128 个用例全过（含 T01–T08 的 104 个）。
  另用 `tools/screenshot.py` 出了一张「放大到 135% 并拖到一侧」的图
  （`assets/screenshots/playing_zoom_pan.png`）人工核对：棋盘确实铺满可视区、
  右侧被裁掉，说明平移生效。
- **结论**：棋盘放大后可自由拖动，且拖动不会被误判成点击；点击手感与之前一致
  （只是判定挪到了松手那一刻）。

## T10 飞出动画的平滑度（切角、圆点、抗锯齿、帧步进）

- **目的**：修掉「线飞出去的时候不够平滑，特别是转弯处」。
  成因是飞出动画的采样方式：整条线是「各节沿自己的折线往前流」，但采样只取
  `s = offset, offset+1, offset+2 …`（每格一个点），拐角落在两个采样点中间时，
  这两点之间会被连成一条**斜弦**，直角被削成斜角；而 `offset` 连续增长，于是这个斜角
  每前进一格就「削平 → 复原」一次（`FLY_SPEED` 下每秒 26 次），看起来就是转弯处在抖。
  用 40 像素格距量了一下：被切掉的线长最多 **23 像素**，且在 0~23 之间来回振荡。
- **用例**：`tests/test_motion.py`（共 22 个）。
- **步骤**：
  1. 折线取段：拐角落在区间里时必须出现在折线顶点上；任何相位下折线长度都等于
     `(节数 - 1) × 格距`（切角会让长度变短，这是一条能抓住切角的硬指标）；
  2. 正式关卡逐关逐箭逐相位（12 关 × 每支箭 × 60 个相位，1000+ 次）比对
     「画布内可见的那一段」与「理论射线路径」的长度是否重合 —— 路径尽头被夹住的部分
     在画布外，不参与比较；
  3. `offset = 0` 时画出的折线必须正好等于线段原来的格心（起飞瞬间不能跳）；
  4. 折线的每一段都横平竖直；`offset` 超过路径尽头时不崩、不画出一坨重复点；
  5. 圆点只补在两端与拐弯处（直线段上补圆点会在节点处胖出 1~2 像素，用像素厚度断言）；
  6. 抗锯齿小图：直径与整数圆同宽、边缘有半透明过渡像素、透明处不渗黑、
     按「形状 + 尺寸 + 颜色」缓存、箭头贴图随尺寸放大；
  7. 位移匀速、与帧率无关（60 帧一步 == 120 帧两步）、任何一帧的位移不超过
     `速度 × MAX_FRAME_DT`（把 `clock.tick` 换成返回 500 毫秒的假时钟验证夹取）；
  8. 残影亮度先淡入再淡出（不能「啪」地蹦到最亮）；端到端点一支能飞的箭、被挡的箭
     各跑完一段动画。
- **预期**：全部通过。
- **实际**：22 个用例全过，全量 150 个用例全过（含 T01–T09 的 128 个）。
  另出两张图人工核对：`playing_flying.png`（飞行中的一帧，线正沿折线滑出、尾迹逐格点亮）
  与新旧渲染的 6 倍放大对照（拐角由「斜切」变成原来的直角、箭头斜边不再有锯齿）。
- **结论**：转弯处不再抖动，线在飞的过程中厚度与折线长度都保持恒定；顺带把盘面静态线段
  的节点疙瘩也去掉了（同一条描边函数），整帧耗时 4.3 ms，未见性能回退。

## T11 箭头与线段的观感（线宽、飞镖箭头、外描边、像素对齐）

- **目的**：把箭头和线段再做一轮美化，对齐参考录屏的观感，并防止「美化」把几何改坏。
  这一轮改了三件事：线宽比例、箭头形状、外描边；顺带修掉一个从 T10 遗留的像素级缺陷。
- **用例**：`tests/test_stroke.py`（26 个函数 / 43 个用例），另更新
  `test_motion.py` 中两条与尺寸相关的断言。
- **步骤**：
  1. **量参考图**：用 ffmpeg 从参考录屏抽帧，逐像素量出线宽与格子间距，定下
     `SEGMENT_WIDTH_RATIO = 0.30`、`MAX_SEGMENT_WIDTH = 15`；
  2. **线宽处处相等**：沿直线段量多行 / 多列的像素带，断言带宽恒等于线宽（即
     直线段上没有鼓包、没有断续）；
  3. **拐点与端头不鼓包**：拐点的实占像素必须恰好等于两条臂的并集，端头的圆头
     只允许往外多出半个线宽；任何位置都不许超出这个并集；
  4. **圆点与线段逐像素对齐**：对同一宽度取 `disc_sprite()`，断言它的像素带与线段
     的像素带完全一致（这是抓「圆点直径比线宽多 1 像素」的那条断言）；
  5. **`stroke_span()` 与 pygame 的取整规则一致**：直接和 `pygame.draw.line` 的实际
     涂色行做对照，防止两端各差 1 像素；
  6. **箭头是飞镖不是三角**：断言 4 个顶点、尾根处的收口点落在凹口里、两枚倒钩
     **前掠**（尖端的投影落在倒钩之前）；顶点顺序绕成闭合多边形；
  7. **箭头尺寸跟着线宽**：`HEAD_SPAN_RATIO / HEAD_LENGTH_RATIO / HEAD_SWEEP_RATIO`
     都实际生效，宽高比不是 1:1，包围盒随线宽单调变大；
  8. **箭头贴图**：包围盒装得下 4 个顶点、贴图尺寸与包围盒一致、边缘有半透明的
     抗锯齿像素、按（方向 + 尺寸 + 颜色 + 外扩量）缓存、外扩量能把图形撑大；
  9. **外描边**：断言描边恰好是一圈（向外多出 `rim_width` 像素、线身内部不多不少）、
     关掉就一圈都不剩；描边宽跟着线宽走；描边色**只压暗不改色相**（比较各通道的
     相对大小），且夜间压得比日间狠；
  10. **飞行与静止一致**：`offset = 0` 时飞行帧画出的线段与静态盘面逐像素相同
      （美化后仍然不跳变）；
  11. **全量渲染不崩**：12 关 × 日夜两套主题各渲染一遍，断言盘面上确实出现了多种
      颜色（不是空盘 / 没画出来）；
  12. **引脚检查**：箭头不会大到跨出自己那一格；飞行中箭头画在线的前端。
- **预期**：全部通过。
- **实际**：43 个用例全过，当轮全量 193 个用例全过。
  另用 `tools/screenshot.py` 重出 12 张截图（README 里用的那批）人工核对：
  线宽、箭头形态、描边浓淡与参考录屏基本一致，两条线挨着的地方也能分清了。
- **结论**：线宽对齐参考图（格距的 0.30），箭头由等腰三角改为飞镖，整支箭加了一圈
  恒定厚度的外描边；拐点 / 端头不再有 1 像素鼓包；静态与飞行的渲染仍然一致。

## T12 界面观感（背景渐变、柔光、投影、卡片、按钮三态）

- **目的**：玩家反馈「界面、背景、按钮等再美化一下」，并防止「美化」把排版或
  交互点坏。原来的界面是一块纯色底 + 一圈硬描边的扁平风格：背景没有任何层次，
  按钮和卡片跟背景糊在一起，按下去除了换个颜色没有任何反馈。
- **用例**：`tests/test_paint.py`（34 个用例）。
- **做法**：新增 `game/paint.py` 提供五样「可缓存」的绘制原语 —— 竖向渐变、
  径向柔光、圆角投影、卡片面（渐变 + 圆角 + 细描边 + 顶部高光 + 投影）、文字阴影；
  配色补进 `theme.py`（渐变两端色、柔光色、栏面色与分隔线、卡片三色、顶部高光、
  投影参数、按钮三段色，日夜各一套）；然后逐个套到背景、棋盘面板、顶栏底栏、
  按钮、菜单面板、滑杆、拨杆与各界面卡片上。
- **步骤**：
  1. **渐变**：两端必须等于给定色、逐行单调、同一行横向完全同色（别把渐变做成斜的）；
     再次调用命中缓存（同一个对象）；
  2. **柔光**：中心 alpha 最亮、向外单调衰减、最边缘接近全透明；所有半透明像素的
     RGB 必须等于柔光自身的颜色（混进黑色就是缩小时渗了黑边）；
  3. **投影**：沿中线往外采样，alpha 单调变淡，最外圈几乎为 0；底图尺寸要算上
     向下偏移的那一截；四周确实变暗，而**卡片本体那一块不许被涂脏**；
  4. **卡片**：圆角真的切掉（角上 alpha=0、正中 alpha=255）、竖向渐变、描边落在
     形状内侧、`alpha<255` 时整块按比例半透明、有投影时 offset 正好等于留白量、
     `draw_card` 落位精准、`draw_panel` 取的是主题的卡片三色；
  5. **缓存**：按参数分键；连续申请 `_CACHE_LIMIT + 40` 张不同尺寸的底图之后，
     条数仍然不超过上限（不然拖滑杆会一路把内存灌满）；
  6. **文字阴影**：垫了阴影之后，被涂到的行数正好往下多出 offset 的量，
     多出来的那几行里确实有投影像素；
  7. **按钮三态**：常态 / 悬停 / 按下三张图的像素必须两两不同；按下时整体下沉
     2 像素（原顶边那两行空了）、并且收起投影；`ghost` 次按钮明显比主按钮「安静」；
  8. **主题**：两套主题的新字段都齐全（3 通道、0~255），`card_shadow` 是
     `(spread, alpha, color, dy)`；夜间背景与按钮确实比日间暗；
  9. **整页渲染**：6 个界面状态 × 日夜两套主题各渲染一遍，不崩、且画面里的颜色数
     超过 6 种（背景退化成一整块纯色会被这条抓住）；背景上下两端的颜色必须不同
     （渐变真的在）；
  10. **排版回归**：菜单 / 设置面板的最后一项离底边至少留 18 像素（真的踩到过
      「最后一项顶在面板底边上」）；开始页「进度卡 → 按钮 → 次按钮」依次不重叠；
      改了 `_item_rect` 的间距之后，点击命中仍然落在正确的菜单项上；
  11. **耗时**：连画 20 帧，平均每帧 < 40 ms（阈值放得很宽，只抓明显回退）。
- **预期**：全部通过。
- **实际**：34 个用例全过，全量 **227 个用例**全过。
  另用 `tools/perf_bench.py` 量了各界面在日夜两套主题下的整帧耗时（缓存建好后的稳态）：
  开始页 3.52 ms、选关页 4.33 ms、第 1 关 2.45 ms、第 12 关 3.44 ms、
  第 12 关飞行中 3.39 ms、菜单展开 5.72 ms、日间第 12 关 3.39 ms，
  都远在 60 FPS 的 16.7 ms 预算之内。
  截图侧新增两张（`settings.png`、`level_clear_day.png`），连同其余 12 张一起重出，
  逐张人工核对过。
- **结论**：背景有了渐变与柔光、棋盘垫在圆角面板上、工具栏变成半透明玻璃并带渐隐
  阴影、按钮与卡片有渐变与投影、按下会下沉；界面层次分明，整帧耗时没有回退。

## T13 开始页四个入口与字母玩法（艺术字、规则页、26 字母关、随机关卡入口、去掉 N 键）

- **目的**：玩家要求美化开始页，并把入口从两个扩到四个 —— 标题「一箭又一箭」改成
  艺术字；下面依次是「规则介绍 / 基础玩法 / 字母玩法 / 随机关卡」。其中字母玩法是
  全新的 26 关，**每一关的盘面拼成对应的大写字母**；随机关卡则是把原来按 `N` 键
  触发的能力**搬到按钮上**，并顺手把 `N` 从快捷键与规则页里彻底删掉。
- **用例**：`tests/test_letters.py`（104 个用例，新增），外加 `tests/test_paint.py`
  里 3 个受影响的用例被改掉（`test_every_screen_renders_with_depth` 从旧的
  「6 个状态」改成新的 8 个状态；原来针对单个「开始按钮 + 开始页选关」的两个用例，
  换成 `test_start_screen_layout_keeps_everything_apart` 与
  `test_art_title_is_drawn_above_the_buttons`）。
- **做法**：
  1. **艺术字**（`game/paint.py` 的 `art_text`）：先按普通字体渲染，再放大
     `ART_SUPERSAMPLE=3` 倍，用「圆盘偏移」把每个偏移点回填一遍做出**等厚描边**
     （`BLEND_RGBA_MAX` 取亮），再把渐变与高光按 alpha 乘上去（`BLEND_RGBA_MULT`），
     最后缩回原尺寸 —— 一次性拿到「描边 + 渐变 + 高光 + 投影」，且不依赖额外字体；
  2. **四个入口**：`game/icons.py` 补 `book` / `play` / `letter_a` / `dice` 四个图标，
     `game/ui.py` 的 `Button` 增加可选 `icon`（画在文字左边，整体仍然居中）；
  3. **字母关**：`game/letters.py` 内置 26 个 5×7 点阵字模，经
     `letter_cells()` 光栅化成棋盘遮罩（`scale=2`、`margin=1` → 16 行 12 列）；
     `game/shapes.py` 的 `cells_of()` 支持 `shape="letter"`，连通性判定对字母关
     **开八连通**（否则 C / S / J / Q 这类斜向相接的字母会被判成断开）；
     `tools/generate_letters.py` 用与基础关相同的逆向构造法批量生成 26 关，
     难度沿字母序递进（`ray_pref` 0.45→0.90、开局可飞上限 0.58→0.30）；
  4. **状态机**：`game/states.py` 扩到 8 个状态（开始 / 规则 / 基础选关 / 字母选关 /
     对局 / 过关 / 失败 / 全清；T20 再加一个入门选关，共 9 个），`main.py` 里用
     `self.track`（"basic" / "letter" / "tutorial"）记录当前走的是哪条线，并把已有
     存档判重沿用 `current_level is levels[level_index]` —— 随机关卡不属于任何列表、
     字母关的 id 是 `"A"`~`"Z"`、入门关是 `"T1"`~`"T3"`，都天然不会和 1~12 撞车；
  5. **去掉 `N` 键**：`_handle_key` 删掉 `K_n` 分支，规则页的快捷键表里也去掉这一行。
- **步骤**（逐条断言）：
  1. **字模**：26 个字母的点阵尺寸一致、每个字母的遮罩都非空、`LETTERS` 是排好序的
     `A`~`Z`；
  2. **遮罩连通**：26 个字母按**八连通**判定全部连通（这条是字母关能不能生成的前提）；
  3. **尺寸顺序**：`board_size()` 返回 **`(行, 列)`** —— 曾经这里返回了 `(列, 行)`，
     直接导致 C / G / J / U / V 五个字母遮罩被裁断、生成失败，所以专门补了一条用例；
  4. **`cells_of`**：`shape="letter"` 与直接调 `letter_cells` 结果一致；
  5. **26 关数据**：每一关都能解（拓扑序可走）、有阻挡、盘面填充率高；
  6. **难度递进**：按字母序的开局可飞占比整体不回升；
  7. **id 不冲突**：字母关 id 全是字符串、基础关 id 全是整数，二者与「不属于任何列表」
     的随机关卡互不干扰；
  8. **开始页**：四个按钮各就各位、标题艺术字在按钮之上、首页统计卡与按钮不重叠；
  9. **规则页**：能进能出（返回键回到开始页），页面里**不再出现 `N` 这一行**，
     `U` / `Esc` 等仍然在；
  10. **选关**：基础入口进 12 关、字母入口进 26 关；点字母网格能进对应关；
  11. **端到端**：字母关通关后**会**写进存档；随机关卡通关后**不会**污染进度；
  12. **`N` 键退出历史舞台**：直接发一个 `K_n` 事件，当前状态不许发生变化；
  13. **渲染**：规则页、字母关（含 A 与 M）都能离屏画出图，且字母关的盘面**真的呈现
     出字母形状**（不再是随便一块矩形）。
- **预期**：全部通过。
- **实际**：104 个新用例 + 3 个改造后的用例全过，全量 **332 个用例**全过（11.0 s）。
  另用 `tools/perf_bench.py` 量了新增界面的整帧耗时：开始页（艺术字）2.26 ms、
  规则页 6.66 ms、基础选关 4.44 ms、字母选关 1.70 ms、字母 A 关静态 2.35 ms /
  飞行 2.36 ms、第 1 关 2.57 ms、第 12 关 3.59 ms、菜单展开 6.53 ms，
  最贵的规则页（一整屏文字重绘）也远在 60 FPS 的 16.7 ms 预算之内。
  截图重出 20 张（新增 `rules.png`、`rules_day.png`、`letter_select.png`、
  `letter_select_day.png`、`playing_letter_a.png`、`playing_letter_m.png`），逐张人工核对。
- **结论**：开始页从「两个按钮」变成「艺术字标题 + 四个入口 + 进度统计」；规则页、
  基础 12 关、字母 26 关、随机关卡四条线各有独立入口且互不干扰；`N` 键彻底移除。

## T15 棋盘格子数整体加密到约 1.4 倍

- **目的**：玩家要求「棋盘格子数增加」。按 640×1140 画布实算后，选的是
  **两条线一起加密到约 1.4 倍** —— 格子从 44 px 降到 31 px、线宽从 13 px 降到
  9 px，棋盘仍然铺满屏幕，只是更精细。
- **用例**：`tests/test_generator.py` 新增
  `test_basic_levels_use_the_denser_grid`、
  `test_random_levels_also_use_the_denser_grid`；
  `tests/test_letters.py` 里写死旧尺寸的 4 条（`test_board_size_is_rows_then_cols`
  等）同步改成新尺寸。
- **做法**：
  1. **字母关**：`game/letters.py` 的 `DEFAULT_SCALE` 2 → 3，棋盘 16×12 → **23×17**
     （391 格）；字母笔画从 2 格宽变成 3 格宽，斜笔明显平滑了；
  2. **基础关**：`tools/generate_levels.py` 的 `PLAN` 尺寸整体放大
     （12×9 → 17×13，15×15 → 21×21，18×13 → 25×19），从 **16×13 到 25×21**；
     箭数 17~55（平均 29.0，原来 15.9）；
  3. **随机关**：`generator.RANDOM_SHAPES` 与 `random_level()` 的尺寸同步放大，
     否则从开始页「随机关卡」进去还是老盘面；
  4. `MAX_PIECE` 从 14 放宽到 20 —— 放大后笔画宽了，一支箭可以吃更长而不吞掉整条笔画。
- **步骤**：
  1. 12 关基础关：每行断言 `rows >= 16`、`cols >= 13`、遮罩 ≥ 150 格、箭数 ≥ 20；
  2. 随机关尺寸表：同上三条逐项断言；
  3. 26 个字母在 `scale=3` 下遮罩**全部八连通**（这是能生成的前提）；
  4. 全量重跑：26 关字母关与 12 关基础关都要「能解 + 有阻挡 + 填充率达标」
     （这几条是 T13 / 旧有用例，加密后照旧适用）。
- **预期**：全部通过，且难度曲线不回升。
- **实际**：
  - 第一轮生成**挂了一条**：`test_basic_levels_keep_the_difficulty_curve`
    报第 11 关（圆环 21×21）的开局可飞比第 10 关高。原因是每关都在自己的
    上限内独立挑「铺得最满」的一版，**实际值可能反而比上一关高** —— 第 10 关上限
    0.15 拿到了 13%，第 11 关上限 0.13 却因为形状所限只拿到 14.6%。
  - 修法：把上限改成**跟着上一关的实际值往下压**（`prev_free - FREE_MARGIN`）。
    但压下去之后同一个种子未必够得到（环形 21×21 用原种子只能到 14.6%，换种子能到
    10.8%），所以再补一层**换种子重试**（`SEED_STEP=100003`、最多 6 次），
    并且在候选中按 `(是否满足上限, 填充率)` 取最优 —— 只压难度会让第 11 关的填充率
    掉到 0.887，两个指标得一起挑。
  - 终版 12 关：开局可飞 **62% → 11% 严格递减**，填充率 0.928 ~ 0.968，
    全程 `EXIT=0`。
  - 全量 **338 个用例**全过（12.5 s）。
- **性能**：格子多了约九成，最贵的一档从 3.32 ms 涨到 **6.02 ms**（第 12 关静态），
  仍在 16.7 ms 预算的三分之一。放大到最大时横向溢出 0（12 关全部不溢出），

## T16 靶心按钮返回来处 + 卡通贴纸风拼装标题

  1. 玩**随机关卡**时点顶栏靶心，没有回开始页，而是掉进了基础选关页；
  2. 玩家给了一张参考截图，要开始页标题换成那种「卡通贴纸」观感（奶白字面、
     粗深描边、浅色外圈、两个「一」画成红 / 蓝圆头横杠、末尾的「箭」换绿色）。
- **用例**：`tests/test_letters.py` 改 1 条、新增 2 条；`tests/test_paint.py`
  改 1 条、新增 4 条。
- **做法**：
  1. **返回来处**：`main.py` 加 `self.play_origin`，三个入口各自登记来路
     （基础选关页 / 字母选关页 / 开始页），顶栏靶心改接新的 `leave_level()`，
     按来路分派。原先接的 `open_select()` 是「按 track 分派」，而随机关卡借用了
     basic 这条线，于是被当成基础关塞进了基础选关页。
  2. **双层描边**：`art_text` 新增 `outline2` / `outline2_width`。外圈按
     `outline_width + outline2_width` 铺一个大圆盘，内圈再按 `outline_width`
     盖上去，于是只看得见 `outline2_width` 那一圈。
  3. **`lift`：描边下移、字面不动** —— 底部那圈边比顶部厚，字看起来浮在边上。
  4. **胶囊横条**：新增 `art_bar()`，复用同一套渲染栈（超采样 + 双层描边 +
     竖向渐变 + 顶部高光），`pad` 算法与 `art_text` 逐项对齐，两者高度天然相等。
  5. **拼装**：新增 `art_banner()`，把字符与横条横着排；`main._start_title_pieces()`
     给出「红条 / 箭 / 又 / 蓝条 / 绿箭」五片。
- **步骤**（逐条断言）：
  1. **随机关回开始页**：走完整点击链路（`MOUSEBUTTONDOWN` 打到
     `hud.select_button.rect.center`），断言 `state == START` 且
     `play_origin == START`；
  2. **来路不会被上一次污染**：玩过随机之后再从基础选关页进关，靶心要回基础选关页；
  3. **三条路线各回各处**：基础 → 基础选关页，字母 → 字母选关页，随机 → 开始页；
  4. **贴纸标题的像素特征**：画在按钮上方、左右不顶边、宽度占屏 > 70%，
     且奶白字面 / 深色内边 / 红条 / 蓝条 / 绿色收尾五种颜色都能在图上找到，
     字面还是上亮下暗；
  5. **横条是圆头胶囊**：正中是字面色，四角是透明的（方头的话那里会有颜色），
     垂直中线上找得到深色内边；
  6. **拼装按墨迹排布**：两张同字拼起来的宽度**恰好**等于「单片墨迹宽 × 2 + gap」，
     且整块画布已贴着墨迹（若改成按 surface 宽度累加，会凭空多出两倍的描边留白）；
  7. **双层描边**：双描边版本的图更大，且纯白像素从 0 变成 ≥ 100（外圈那一环）；
  8. **`lift` 真的把边推下去了**：取「口」的中间一列，比较字面顶边到墨迹顶边、
     与字面底边到墨迹底边的距离 —— 底部必须更厚，且比不加 `lift` 时更厚。
- **预期**：全部通过。
- **实际**：
  - 中间踩了两个坑，都记在 `docs/design.md` 8.7.3：
    1. **描边宽度的单位曾经是「超采样像素」**，而 `pad` 是「原始像素」——
       `stamp` 的调用处没有乘 `s`，于是标称 6 px 的描边实际只有 2 px，
       外圈更是细到缩回后被平均成灰色（实测只有 `(205,205,206)`）。统一成
       原始像素后描边才真的粗起来。
    2. 单位统一后圆盘半径变成 18（超采样像素），**逐点 blit 一次要 42 ms**，
       五个字符就是 210 ms。改法是在 1/2 分辨率上做膨胀（偏移点数与单点面积
       各降到 1/4，总开销约 1/16），再放大回来 —— 边缘被插值柔化，对一层纯色
       描边反倒更像抗锯齿。整页首帧 210 ms → **62 ms**，稳态 **3.1 ms**。
  - 另外补了一个测试基建问题：`tests/test_paint.py` 的 `game` fixture 收尾会
    `pygame.quit()`，新写的几条直接调 `pygame.font.SysFont` 的用例会报
    `font not initialized`，于是加了 `big_font()` 兜底 re-init。
  - 全量 **344 个用例**全过（16.0 s）。
- **性能**：`tools/perf_bench.py` 重跑 —— 开始页 2.90 ms（原 2.24，多了一层描边）、
  规则页 7.55 ms、菜单展开 9.12 ms（最贵），全部远在 16.7 ms 预算内。
- **结论**：顶栏靶心现在是名副其实的「返回」；标题从「一段渐变文字」变成
  五片拼装的贴纸字，配色与结构都由 `theme` 提供，日夜两套底色上同样清晰。

- **结论**：开始页现在是「薄荷青/深蓝底 + 同色箭形暗纹 + 贴纸标题 + 卡通箭吉祥物 +

## T22 入门关改成随机散铺：盘面必须「不规律」且来自逆向构造

- **目的**：T21 把入门三关铺到了「盖住棋盘一半以上」，但摆法是**按图案码**的 ——
  第 1 关每行一条朝右的链、第 2 关上半朝上 / 下半朝下、第 3 关横行纵列交叉。
  用户反馈「入门玩法关卡设计不要太有规律」：铺满率够了，一眼看去却像一张图纸。
- **用例**：
  1. `test_tutorial_boards_are_not_laid_out_in_a_regular_pattern`（新）—— 五条硬指标：
     整行 / 整列同向的条带 0、2×2 四格同向的小方块 0、横竖相邻同向最长段 ≤ 3、
     四个方向都出现且最多的不超过 35%、开局可飞 18% ~ 42%；
  2. `test_tutorial_boards_are_built_by_reverse_construction`（新）—— 拿
     `TUTORIAL_PLAN` 的 seed 重跑散铺器、逐个格子比对关卡数据，再把**放箭顺序倒过来**
     自己在真棋盘上走一遍；
  3. `test_tutorial_boards_are_dense_and_never_leave_a_deadlock`（改注释）—— 盘面是
     随机散铺出来的，求解器给的那条顺序仍要完整走得通；
  4. `test_tutorial_levels_fill_over_half_the_board`（保留）—— 铺满率、3 颗红心、
     单格箭、开局有箭被挡着、`verify_solution` 通过。
- **步骤**：先把「不规律」量化成可测指标，再拿几千个种子筛：
  - 逆向构造（放箭时箭头前方的射线上不许有已放好的箭）保证可解，不用事后搜解；
  - 落点评分 `alpha × 走廊长度 + (1-alpha) × 随机`，扫 0 / 0.15 / 0.3 / 0.45 / 0.6 / 0.8 六档；
  - 按五条指标筛种子，取「开局可飞」最接近理想值的那一版写进 `TUTORIAL_PLAN`。
- **预期**：五条指标全过，且逐格复现一致。
- **实际**：全量 **370 个用例**全过（25 s）。过程中量到的几件事：
  - **alpha 两头都不能去**：取 0（纯随机）开局可飞占到 49% ~ 54%，乱点也能过；取 1
    （永远挑走廊最长的落点）可飞能压到 13% ~ 17%，但候选按走廊长度排序后反而排出一
    排排同向的条带 —— 条带数从 0 涨到 157 ~ 189 条，等于又回到「有规律」。0.30 ~ 0.45
    落在中间：可飞 23% ~ 37%、条带 0；
  - 旧盘面的实测值：条带 **12 / 7 / 6**、同向方块 **15 / 16 / 0**、最长同向串 6 / 5 / 8、
    方向峰值 **100% / 43% / 50%** —— 新指标里前四条都抓得住它；
  - 搜一遍种子要 **65 s**（3000 个种子 × 3 关），所以种子写死在表里：三关导入时构建
    加求解一共 **0.020 s**；
  - **踩到一个地雷**：`game/level.py` 是被 `tools/generate_levels.py` **整份重写**的
    （`dump()` 只写 HEADER + LEVELS + SHAPE_LABELS），而入门三关当时正手写在那个文件
    里 —— 跑一次 `python tools/generate_levels.py` 就会把关卡数据连同入门玩法一起抹掉。
    改成 `game/tutorial.py` 单独成模块，`level.py` 末尾只留一行转发导入，生成脚本的
    `dump()` 里补上同样三行。验证方式是拿现成的 `LEVELS` 调一遍 `dump()` 写到临时文件，
    与 `game/level.py` **逐字节比对**：46426 == 46426，`True`。
- **结论**：把「不规律」当成和「铺满率」一样的可测指标写进测试才守得住 —— 数值上
  「没超界、有阻挡、铺得满」全都不假，但看着就是一张图纸。

## 未覆盖 / 已知限制

- `game/audio.py` 的音效只在有真实音频设备时才会响，测试环境用 dummy 驱动，只验证了
  「初始化失败时不崩溃」。
- `game/hud.py`、`game/icons.py` 的**具体画法**仍然主要靠 `tools/screenshot.py` 离屏出图
  人工核对（顶栏 / 底栏 / 菜单 / 设置 / 日间主题各出一张图）；现在只对顶栏那几个图标
  断言了「画出来 ≥ 24 个像素」（T21，抓「画了个寂寞」），图案长什么样没有逐像素断言。
  它们依赖的 `game/paint.py` 原语（渐变 / 柔光 / 投影 / 卡片）已经有像素级测试（T12）。
- `game/paint.py` 的贴图缓存是模块级的全局字典，键里包含了全部颜色参数，所以切主题、
  改配色都会自然命中新键。**代价是**：如果以后给它加一个「不带颜色」的参数（比如随
  时间变化的动画量），记得那个键要显式塞进时间戳，否则会一直返回第一帧的贴图。
- 随机关卡的质量依赖随机种子，`random_level()` 有兜底逻辑（逐个形状重试 + 矩形退化），
  但没有对「每一局都必然生成成功」做穷举验证。
- **文字没有缓存**：`_draw_text` / `text_shadow` 每帧都现 `font.render`，规则页正文
  折到 6 行之后这一项约 1 ms。文字内容是静态的，真要压可以按（字体, 文字, 颜色）
  缓存一张贴图，只是目前没必要 —— 中位 8.89 ms 离 16.7 ms 还远。
- 入门三关的种子是**离线筛出来的**（`game/tutorial.py` 的 `TUTORIAL_PLAN`），没有
  配一个像 `tools/generate_levels.py` 那样的重生成脚本：要换盘面得改种子，或者按
  `docs/design.md` §9.5 的步骤重跑一遍筛选（约一分钟）。测试只保证「当前这组种子
  满足全部指标」，不保证「随便换个种子也能筛出来」。
- `T` 是**全局**快捷键（见 8.11）：现在这个游戏没有任何文字输入框，所以不冲突。
  以后如果要加输入框（命名存档、搜索关卡之类），记得在「正在输入」时把它挡掉 ——
  否则玩家打字打出一堆 `t` 会顺手把主题来回切。
- 「按键功能」表里那个小拨杆只断言了「位置对、不压字、画得出像素」，它长什么样
  （药丸弧度、太阳光线的长短）仍然靠 `rules.png` / `rules_day.png` 人工核对。
