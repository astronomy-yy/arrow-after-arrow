# 测试记录（T01 – T09）

- 运行环境：Windows 11 / Python 3.14.0 / pygame-ce 2.5.8 / pytest 9.x
- 运行方式：项目根目录执行 `python -m pytest -q`（测试在 SDL dummy 驱动下无窗口运行）

## T01 路径检测：四方向无阻挡 / 贴边出界

- **目的**：验证 `Board.can_fly` 在箭头前方没有别的线段时返回 `True`，包括箭头贴在棋盘边上、下一步就出界的情况。
- **用例**：`tests/test_path.py::test_four_directions_clear`、`test_edge_flies_out[0-0-U / 4-4-D / 0-4-L / 4-0-R]`
- **步骤**：构造 5×5 空棋盘，放一支贴在边缘、朝向盘外的箭，调用 `can_fly`。
- **预期**：四个方向、四条边，全部返回 `True`。
- **实际**：5 个用例全过。
- **结论**：出界判定与 `in_bounds` 拼接正确，没有数组越界。

## T02 路径检测：被线段挡住

- **目的**：验证箭头射线上有别的线段时返回 `False`，且判断会穿透整条射线而不只看下一格。
- **用例**：`test_blocked_four_directions[head0-U / head1-D / head2-L / head3-R]`、`test_segment_body_blocks`
- **步骤**：
  1. 在箭头正前方 2 格处放一支「自己朝外能飞」的箭，检查原箭被挡、阻挡者能飞；
  2. 放一条竖折线，让它的一段身体落在横箭的射线上，检查横箭被挡。
- **预期**：被挡方 `False`，阻挡方 `True`（说明挡住的判定来自别人的**身体**，不是别人也飞不出去）。
- **实际**：5 个用例全过。
- **结论**：射线是从箭头下一格一直扫到出界，正确。

## T03 折线箭沿自身轨迹滑出，而不是横向扫过

- **目的**：本项目最核心的一条规则 —— 线段拐弯时，身体只沿自己的格子前进，不会横扫旁边的格子。
- **用例**：`test_bent_flows_along_own_path`、`test_bent_head_ray_blocked`
- **步骤**：构造 L 形箭 `(2,0)→(2,1)→(1,1)`，箭头朝上：
  1. 在尾格旁边 `(1,0)` 放一支箭 —— 它不在 L 形的滑出路径上；
  2. 把箭改放到 `(0,1)` —— 正好压在箭头射线上。
- **预期**：情形 1 两支都能飞；情形 2 L 形被挡。
- **实际**：两个用例全过。
- **结论**：判定只看箭头那一条射线，身体不参与碰撞。

## T04 关卡生成器：造型遮罩 + 可通关性 + 填充率

- **目的**：确认 8 种造型的遮罩合法且四连通；生成出来的每一关都真的可通关；盘面密度对齐参考游戏。
- **用例**：`tests/test_generator.py`（共 17 个）
- **步骤**：
  1. 对 rect / round / diamond / heart / triangle / cross / hourglass / ring 逐个取 13×13 遮罩，检查格子都在棋盘内、且四连通；
  2. 生成 4 种造型的关卡，逐条检查：每支箭 ≥2 格、方向字符合法、格子全在遮罩内、相邻格曼哈顿距离为 1；
  3. 用 `verify_solution()` 拿真棋盘按 `solution` 模拟点一遍；
  4. 独立用 `solver.solve()` 再解一遍做交叉验证；
  5. 检查填充率 ≥ 0.85。
- **预期**：全部满足。
- **实际**：全过。当前 12 关的实际填充率为 0.94 ~ 1.00（`tools/generate_levels.py --stats` 输出）。
- **结论**：逆向构造法有效；「生成器说可解」和「求解器独立求解」两条路径互相印证。

> **附：填充率调优过程。** 最初线段短、直行多，盘面很稀疏（第 3 关只铺到 0.53），
> 与参考录屏「密密麻麻铺满」的观感差距明显。把 `straight_bias` 从 0.62 降到 0.24、
> `max_piece` 提到 26 之后，长箭绕来绕去反而把棋盘铺得更满，同时因为拐弯频繁，
> 观感上仍然是「一堆短折线缠在一起」而不是几根长横条。
> 这一版的密度达标了，却把玩法弄丢了（盘面没有阻挡），见 T08。

## T05 AI 求解器：有解 / 无解 / 提示

- **目的**：验证求解器能找到完整通关顺序，无解局面如实返回 `None`，提示退化为「随便挑一支能飞的」。
- **用例**：`test_solver_clears_generated_levels[0/4/8]`、`test_solver_reports_unsolvable_board`、`test_next_move_prefers_solvable_step`、`test_apply_solution_rejects_bad_order`、`test_solve_empty_board`
- **步骤**：
  1. 对第 1、5、9 关求解，检查返回的 id 集合与盘上箭完全一致，并用 `apply_solution` 真的执行一遍；
  2. 构造两支互相对着、谁也飞不出的箭，检查 `solve` 返回 `None`、`next_move` 返回 `None`；
  3. 让求解器给出第一步，删掉它之后再用 `is_solvable` 确认仍可解（说明给的是「正确」而不是「随便」的一步）。
- **预期**：如上。
- **实际**：全过。
- **结论**：提示与自动通关可以放心共用同一个求解器。

## T06 端到端：合成点击通关一整关

- **目的**：单元测试覆盖不到「点击 → 判定 → 动画 → 判通关」这条接线，用无窗口的完整 `Game` 跑一遍。
- **用例**：`tests/test_game_flow.py`（共 8 个）
- **步骤**：
  1. 用 SDL dummy 驱动创建 `Game`（存档指向临时目录，不碰真实存档）；
  2. 合成 `MOUSEBUTTONDOWN` 事件，坐标取箭头端那一格的像素中心，逐格点击 `solution` 里的箭；
  3. 每次点击后推进主循环，直到飞行动画结束；
  4. 最后一支飞完后断言状态变为 `LEVEL_CLEAR`、星级 ≥1、金币 +2、存档里出现通关记录；
  5. 另外覆盖：点错扣红心 + 撤销恢复、点空格无惩罚、动画期间输入被锁、
     提示扣金币、切主题盘面换色、重开本关与随机关卡。
- **预期**：全部通过。
- **实际**：8 个用例全过。
- **结论**：主流程可用。

## T07 窗口尺寸收敛与缩放响应

- **目的**：修掉「窗口无法调整大小、也拖不动」的缺陷，并防止回归。
  成因是窗口默认高 1000，比桌面（非 DPI 感知进程看到的逻辑尺寸）还高，
  Windows 把窗口垂直居中后标题栏和底边双双跑到屏幕外（实测 `top = −81`、
  `bottom = 958`），用户抓不到边框也抓不到标题栏。
- **用例**：`tests/test_window.py`（共 12 个）
- **步骤**：
  1. 纯函数层：`usable_window_cap()` 是否留出标题栏 / 任务栏余量、
     `fit_to_screen()` 是否等比收敛且从不放大、任意桌面尺寸下结果都放得下；
  2. 环境识别：dummy 驱动会谎报 1024×768，`desktop_size()` 必须返回 `None`，
     否则截图与测试环境的窗口会被误缩小；
  3. 接入 `Game`：monkeypatch 成 1440×900 的桌面，断言初始窗口与最小尺寸都在
     `usable_window_cap()` 之内；dummy 环境下断言尺寸仍为默认值（截图不受影响）；
  4. 缩放响应：`_resize()` 后窗口尺寸、`view_scale`、`view_rect` 都跟着更新；
     拖到下限以下会被夹到 `min_window`，且不会反复重建窗口；
  5. 尺寸与当前 surface 一致时不调用 `set_mode`（拖拽期间不重建窗口）；
  6. 缩放后点击映射仍然精准（画布坐标 → 窗口坐标 → 反算命中格）。
- **预期**：全部通过。
- **实际**：12 个用例全过；另用真实窗口 + Win32 `MoveWindow` 做了一次端到端
  回归（窗口外框落在 `top = 39`、`bottom = 838`，上下边框均回到屏幕内）。
- **结论**：窗口可正常拖拽缩放；无窗口环境（截图 / CI）行为不变。

## T08 关卡阻挡与难度曲线（含求解器重写）

- **目的**：修掉「关卡互相没有阻挡、无脑乱点必通关」的缺陷，并防止回归。
  成因是生成器的第二条放置约束（身体不许压在已放好箭的射线上），它和第一条
  （自己的射线上不能有已放好的箭）合起来等价于对任意两支箭 `射线(a) ∩ 身体(b) = ∅`，
  于是开局每一支箭都能直接飞出去，**阻挡在数学上不可能出现**。
- **用例**：`tests/test_blocking.py`（共 29 个），另改动 `test_game_flow.py` 中
  一条把该 bug 当成预期行为的旧用例。
- **步骤**：
  1. 诊断：对 12 关逐关统计开局可飞箭数、被挡箭比例、平均每支箭被几支挡住 ——
     改之前量到的是**全部 100% 可飞、0% 被挡**；
  2. 删掉第二条约束后，用「箭头前方空走廊长度」的偏好度 `ray_pref` 当难度旋钮，
     扫参对照填充率：`ray_pref` 0 → 1 时开局可飞 99% → 22%、被挡 0.9% → 78%，
     填充率反而 0.924 → 0.965；
  3. 为每个关卡配 `ray_pref` 与「开局可飞上限」，重生成 12 关，检查难度逐关递减；
  4. 断言正式关卡「必须有能点的，也必须有点不动的」，且被挡比例 ≥ 0.25；
  5. 求解器：用「一条 A 被 B 挡、B 被 C 挡的链」断言只能从 C 开始（`solve` 返回
     `[2, 1, 0]`）；用「两支互相封死」断言返回 `None`；断言求解器算出的
     「入度为 0」集合与棋盘自己的可飞集合完全一致；对 12 关全量求解并真的执行一遍；
     对最大的关卡断言求解耗时 < 0.5 s；
  6. 生成器：断言 `ray_pref=1` 时被挡比例 ≥ 0.5、`ray_pref=0` 时 ≤ 0.2（旋钮真的起作用）；
     断言重阻挡不会生成死局（`verify_solution` 与 `solve` 双通过）。
- **预期**：全部通过。
- **实际**：29 个用例全过。12 关的「开局可飞」比例为
  67% → 58% → 50% → 50% → 42% → 31% → 28% → 21% → 20% → 15% → 14% → 11%，
  逐关严格不回升；被挡比例 33% ~ 89%，平均每支箭被 1.73 支箭挡住；
  填充率 0.94 ~ 1.00。最大的一关求解耗时 < 0.01 s。
- **结论**：关卡现在必须排出先后顺序才能通关；提示与 AI 自动求解在有阻挡的盘面上
  也能毫秒级给出正确解。

> **附：顺带修掉的求解器缺陷。** 原来的求解器是「深度优先搜索 + 失败局面记忆化」，
> 在无阻挡的盘面上看着没问题（随便一条路都通），但那是假象：每步平均四五支可飞、
> 深度一二十层，搜索树指数爆炸，60 万节点的上限瞬间打满，于是**有解的关卡被判成无解**，
> 提示与自动求解直接失效。改成「谁挡谁」建图 + Kahn 拓扑排序后，O(n²) 精确判定：
> 图无环则任意拓扑序都是解，图有环（互相封死）才真的无解。

## T09 棋盘缩放与拖动（含「点 vs 拖」判定）

- **目的**：修掉「棋盘能放大缩小，但拖不动」的缺陷，并防止回归。
  成因是 `_compute_geometry()` 只按缩放算出居中坐标，没有任何平移量，而放到最大时
  **12 关每一关都横向溢出可视区**（131~171 像素，其中 5 关纵向也溢出 158~252 像素），
  溢出的部分用户看不到也够不着。修的时候还得同时解决「拖棋盘」与「点击线段让它飞」的
  冲突 —— 正式关卡填充率 0.94~1.00，若按下即点，想拖棋盘就一定先点飞一支箭。
- **用例**：`tests/test_pan.py`（共 24 个），另改动 `test_game_flow.py` 的点击合成方式
  （从只发 `MOUSEBUTTONDOWN` 改成成对发「按下 + 抬起」）。
- **步骤**：
  1. 前提：断言默认缩放下 `_can_drag()` 为假（棋盘本来放得下），放到最大后为真且
     `board_pixel_w > 可视区宽`；缩小到 `ZOOM_MIN` 时位置锁死在居中、`pan_by()` 返回 False；
  2. 拖动：从线段格心按住拖 (60, 40)，断言棋盘精确平移 (60, 40)、线段一支不少、红心不扣、
     无飞行动画（拖动绝不能误触发点击）；中键 / 右键拖动同样生效；
  3. 点 vs 拖：只按下不松手不触发；按下后原样松手正常飞出；手抖 `DRAG_THRESHOLD - 1`
     像素仍算点击；位移超过阈值则这次点击作废，不会误飞；
  4. 边界：往 ±6000 像素猛拖，断言棋盘始终落在夹取区间内、可视区里永远留着能点的格子
     （不会被拖出屏幕找不回来）；拖到边界后往回拖 10 像素，棋盘必须立刻跟 10 像素
     （`pan` 已写回夹取值，不会「粘住空转」）；
  5. 缩放的锚点：锚在指针上缩放时，指针底下那个棋盘位置在缩放前后偏差 < 0.005，
     且明显优于「按中心缩放」的偏差；滚轮上下滚动同样锚定指针，并夹在缩放区间内；
  6. 复位：滚轮缩回 100%、`0` 键复位、缩小到装得下、换关、重开时 `pan` 都归零、棋盘
     回到正中；方向键平移与 `+` `-` 缩放按固定步长生效；
  7. 拖动后再做格心命中测试（画布坐标 → 命中格）仍然精准。
- **预期**：全部通过。
- **实际**：24 个用例全过，全量 128 个用例全过（含 T01–T08 的 104 个）。
  另用 `tools/screenshot.py` 出了一张「放大到 135% 并拖到一侧」的图
  （`assets/screenshots/playing_zoom_pan.png`）人工核对：棋盘确实铺满可视区、
  右侧被裁掉，说明平移生效。
- **结论**：棋盘放大后可自由拖动，且拖动不会被误判成点击；点击手感与之前一致
  （只是判定挪到了松手那一刻）。
