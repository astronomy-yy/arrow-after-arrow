# 一箭又一箭 —— 设计说明

## 2. 数据结构

### 2.1 线段箭

一条线段箭不是「一个格子的箭头」，而是**一条能拐弯的折线**：

```python
{
    "cells": [[3, 5], [3, 6], [4, 6], [4, 7]],  # 尾端 -> 箭头端，逐格上下左右相连
    "dir": "R",        # 箭头朝向 U / D / L / R
    "color": 4,        # ARROW_PALETTE 的颜色索引
}
```

- 最后一个格子是**箭头端**，`dir` 描述箭头从这一格往哪边飞；
- 其余格子是**身体**，飞行时身体只沿自己的折线依次前进，**不会横向扫过旁边的格子**。

### 2.2 关卡

```python
{
    "id": 9, "name": "第9关 大盘如月", "shape": "round",
    "mistakes": 3, "rows": 15, "cols": 15,
    "seed": 9909072, "time_limit": 320,
    "arrows": [ ... ],
    "solution": [19, 18, ..., 0],   # 一条已验证的通关顺序
}
```

`shape` 是造型名，交给 `game/shapes.py` 展开成遮罩格子集合；线段只会铺在遮罩内，
底部的辅助线点阵也只画在遮罩格上 —— 这一条就让整个棋盘呈现「圆」「心」等造型，
和参考录屏里的关卡构图一致。

### 2.3 棋盘 Board

- `_occ[rows][cols]`：每格属于哪一支箭，空格为 `None`；
- `arrows`：还留在盘上的箭；
- `wrong_ids`：点错过的箭，界面把它涂成暗红并常驻显示；
- `_history`：撤销栈，每次出手前压一份快照（活着的箭 id 列表 + 红心数 + 错标集合）。

## 3. 核心规则：射线检测

线段箭沿自身折线滑出时，身体只经过自己原来的格子，所以「能不能飞出去」只取决于
**箭头端朝向上有没有别的线段**：

```text
函数 can_fly_arrow(arrow):
    (dr, dc) = 方向增量(U:-1,0 / D:1,0 / L:0,-1 / R:0,1)
    (r, c) = arrow.head + (dr, dc)
    当 (r, c) 仍在棋盘内时循环:
        若 _occ[r][c] 上有别的箭: 返回 False（被挡住）
        (r, c) += (dr, dc)
    出界都没遇到别的箭: 返回 True
```

这正是参考游戏的判定方式：被挡时线段会朝箭头方向冲一下再弹回，扣一颗红心，
并且那支箭在此后一直保持暗红标记，方便玩家记住「这条路走不通」。

## 4. 关卡生成：逆向构造法

手摆关卡几乎不可能保证「必然可通关」，所以关卡全部由算法生成。

**正向规则**：若线段 B 挡在 A 的箭头射线上，则 B 必须先于 A 被清除。
直接按这个规则正向搜索很难构造出又满又可解的盘面，于是反过来做：

1. 从空棋盘开始，一支一支把箭「放」回去，**放箭顺序 = 通关顺序的倒序**；
2. 放第 k 支箭时只要求一件事：**它自己的箭头射线上没有已经放好的箭**；
3. 这一条恰好等价于「按放置顺序倒着点，每一步的射线都是空的」——第 k 支箭飞的
   时候，留在盘上的正是比它早放的那 k-1 支，而它在放置那一刻就确认过躲开了
   这些箭，所以关卡必然可通关；
4. 落点用「代价优先 + 小窗口随机」，兼顾**铺得满**与**每局不一样**；
5. 单支箭的身体从箭头端往回生长，`straight_bias` 只有 0.24 —— 也就是每一步
   七成以上概率拐弯，于是长箭也不会变成一根长横条，而是绕来绕去的折线。

### 4.1 阻挡是设计目标，不是副产品

早期版本在放置时还加了第二条约束：**箭的身体也不许落在已放好箭的射线上**。
它看起来像是在「预留空走廊」，实际上和第一条合起来等价于

```text
射线(a) ∩ 身体(b) = ∅          （对任意两支箭 a、b）
```

也就是每支箭的出口走廊永远是空的：开局全盘任何一支都能直接飞出去，
**点什么都对，关卡退化成「无脑乱点必通关」**。这条约束对可通关性毫无贡献，
纯属把玩法抹掉，已经删除。

删掉之后，**后放的箭（先点）可以名正言顺地站在先放的箭（后点）的射线上**，
这就是盘面上的阻挡与先后依赖 —— 也正是参考录屏里的样子：箭头常常直接顶在
别的线段上。

难度由一个旋钮控制：`ray_pref` —— 挑落点时偏好「箭头前方空走廊长」还是
「短」。走廊越长，越容易被后面放的箭压住，阻挡就越多。实测：

| `ray_pref` | 开局能直接飞的比例 | 被挡箭比例 | 填充率 |
|---|---|---|---|
| 0.0 | 99% | 0.9% | 0.924 |
| 0.5 | 57% | 43% | 0.950 |
| 1.0 | 22% | 78% | 0.965 |

注意填充率是**跟着一起涨**的：走廊长意味着那些格子会被后面放的箭填满，
「铺得满」与「有阻挡」并不矛盾，反而互相成全。

### 4.2 关键参数

参数都在 `game/generator.py` 的 `DEFAULT_STYLE`：

| 参数 | 值 | 作用 |
|---|---|---|
| `max_piece` | 26 | 单支箭最长格数 |
| `straight_bias` | 0.24 | 继续直行的概率，越小拐弯越密 |
| `stop_chance` | 0.03 | 提前收尾的概率 |
| `window` | 4 | 在「最省的 N 个候选」里随机挑，控制贪心程度 |
| `ray_pref` | 0.65 | 偏好长走廊的程度，越大阻挡越多 |

| 第7关 | 矩形 | 25 | 0.988 | 7 (28%) | 72% | 1.96 |
| 第8关 | 三角 | 14 | 0.976 | 3 (21%) | 79% | 2.43 |
| 第9关 | 圆形 | 25 | 0.960 | 5 (20%) | 80% | 2.44 |
| 第10关 | 沙漏 | 13 | 0.976 | 2 (15%) | 85% | 2.15 |

模拟点一遍，`solver.solve()` 再独立解一遍，两边都过才写进 `game/level.py`。

## 5. 可解性与 AI 求解：拓扑排序

一支箭能不能飞只取决于箭头射线上有没有别的箭；飞出去只是把自己从盘上拿掉，
不会动别人。所以可以定义一个有向关系 `a 挡 b`，整个问题退化成拓扑排序：

- 图**无环** → 任意一个拓扑序都是一条通关顺序；
- 图**有环**（两支箭互相封死）→ 环里谁都不能先走，必然无解。

`game/solver.py` 用 Kahn 算法跑一遍，O(n²)，最大的关卡 25 支箭也是毫秒级。

这里曾经写的是「深度优先搜索 + 失败局面记忆化」。在**无阻挡**的盘面上它看着
挺好用 —— 但那是假象：每步平均四五支可飞、深度一二十层，搜索树指数爆炸，
60 万节点的上限瞬间打满，于是**明明有解的关卡被报成无解**，提示与 AI 自动求解
全部失效（而当时的测试恰好只跑在无阻挡的关卡上，所以一直没暴露）。
换成拓扑排序后，正确性和速度都变成确定的。

## 6. 界面布局

- **顶栏**：设置齿轮（左上）· 日夜拨杆 · 关卡标题 + 金色关卡号 · 红心 ×3 ·
  倒计时 · 手柄（跳关）· `⋯`（菜单）· 靶心（关卡选择）。
- **棋盘**：中部自适应缩放，按 `MAX_CELL_SIZE` 上限等比铺满可用区域，
  底部滑杆可以手动缩放，放大后按住棋盘即可拖动（见 6.2）；辅助线点阵画在造型
  遮罩的格心。
- **底栏**：金币 + 提示（左上）· 缩小 / 滑杆 / 放大（中部）· 辅助线开关（右上）。
- **绘制全部由代码完成**：图标是 `game/icons.py` 里的矢量绘制（齿轮、弯月、太阳、
  手柄、时钟、金币、灯泡、`#`），音效是 `game/audio.py` 用 `numpy` 合成的正弦波，
  **项目里没有任何图片或音频素材**，因此不存在素材版权问题。
- **配色**：`game/theme.py` 提供日间 / 夜间两套界面配色；线段箭的颜色由
  `ARROW_PALETTE`（夜间，糖果色）与 `ARROW_PALETTE_DAY`（日间，压深一档）
  两套调色板按主题解析，`Arrow.color` 是属性，切主题时盘上所有箭立即换色。

### 6.1 窗口尺寸：逻辑画布 + 等比缩放

画面永远渲染在固定的逻辑画布 `640 x 1140` 上，`_present()` 再按
`view_scale` 等比缩放贴到窗口中央，`_to_world()` 把鼠标坐标反算回画布坐标
（缩放后点击依然精准，`tests/test_window.py` 有覆盖）。因此窗口怎么拖都不影响
布局，改变的只是整体缩放系数。

这里踩过一个真实的坑：**窗口默认高 1000，比桌面还高**。进程不是 DPI 感知的，
在缩放 200% 的屏幕上 pygame 看到的桌面只有 `1440 x 900`，而 Windows 会把高过
桌面的窗口垂直居中 —— 结果标题栏跑到屏幕上方之外（`top = -81`）、底边跑到
屏幕下方之外（`bottom = 958`），**用户既抓不到边框去缩放，也抓不到标题栏去拖动**。

现在的做法是 `main.desktop_size()` + `fit_to_screen()`：启动时按桌面尺寸减去
`SCREEN_RESERVE_*` 余量再等比收敛，最小尺寸也一起收敛，保证上下边框都在屏幕内。
另外 `_resize()` 不再无脑调 `set_mode()` —— SDL2 在窗口尺寸变化时本来就会自动换掉
display surface，拖拽过程中反复重建窗口会卡顿、还可能打断 Windows 的模态拖拽
循环；只有尺寸和当前 surface 对不上（比如 dummy 驱动）时才补一次。

### 6.2 棋盘缩放与平移：拖得动，且不会把点击吃掉

底栏滑杆把格子在 `ZOOM_MIN(0.65)` ~ `ZOOM_MAX(1.35)` 之间放大缩小。缩放本身只需
重算格子边长，问题是**放大以后棋盘会溢出可视区**：12 关在最大缩放下无一例外横向
溢出 131~171 像素（其中 5 关纵向也溢出 158~252 像素），溢出部分既看不到也够不着。
所以棋盘几何里多了一个平移量 `self.pan`，几何计算拆成三层：

| 层 | 函数 | 职责 |
|---|---|---|
| 可用区 | `_viewport()` | 顶栏与底栏之间那条 `640 x 874` 的区域，棋盘只能活动在这里面 |
| 零平移基准 | `_base_position()` | 放得下就居中、放不下也居中，作为 `pan` 的参照原点 |
| 夹取 | `_clamp_position()` | 放得下 → 锁死在居中的位置；放不下 → 允许拖到棋盘边缘与可视区边缘对齐为止 |

夹取后的结果会立刻写回 `pan`（而不是留着原始累加值），否则拖到边界再往回拖时，
指针要先「空转」掉之前多拖的那一段，手感像粘住了。

**拖动与点击的冲突**是这块最麻烦的地方。正式关卡填充率 0.94~1.00，几乎每一格都是
线段，如果「按下即点」，那想拖棋盘就一定会先点飞一支箭（被挡的话还白扣一颗心）。
于是把交互改成**按下记账、抬起了结**：

```
MOUSEBUTTONDOWN(左键) → 记下按下的位置与那一格（不动作）
MOUSEMOTION           → 位移超过 DRAG_THRESHOLD(8 逻辑像素) ⇒ 改判为拖动棋盘，点击作废
MOUSEBUTTONUP(左键)   → 仍是这次点击 ⇒ 执行「飞出 / 被挡」判定
```

中键 / 右键按住可以直接拖（不参与点击判定），滚轮缩放锚在鼠标位置上 ——
`_compute_geometry(anchor)` 会记下锚点在棋盘里的相对位置（0~1），缩放后反解出
新的 `pan`，让指针底下的那个位置尽量不动（不锚定的话，缩放永远是围绕中心做，
想放大看角落就得「放大一下、再拖一下」来回倒）。

棋盘比可视区小的时候拖动是**故意不生效**的（位置锁在正中），拖动只在该有用
（放大到溢出的那 5 个档位以上）时才有反应；换关、重开、缩小到装得下时，
`pan` 都会自动归零，棋盘重新摆回中间。

## 7. 动效

| 动效 | 实现 |
|---|---|
| 飞出 | 整条线段预渲染成一张 Surface，按「自身格子 + 箭头延长线」的像素路径平移，出棋盘后继续飞出屏幕并淡出 |
| 残影 | 飞出路径经过棋盘内的部分留一层灰色点阵，滑一段淡一段 |
| 被挡 | 线段沿箭头方向冲出一小段再弹回，同时该箭涂成暗红并常驻标记 |
| 提示 | 目标线段的描边做呼吸式发亮 |
| 自动求解 | 维护一个待点队列，每 0.35 秒自动点一支，动画期间暂停 |
