## 2. 数据结构

### 2.1 线段箭

一条线段箭不是「一个格子的箭头」，而是**一条能拐弯的折线**：

```python
{
    "cells": [[3, 5], [3, 6], [4, 6], [4, 7]],  # 尾端 -> 箭头端，逐格上下左右相连
    "dir": "R",        # 箭头朝向 U / D / L / R
    "color": 4,        # ARROW_PALETTE 的颜色索引
}
```

- 最后一个格子是**箭头端**，`dir` 描述箭头从这一格往哪边飞；
- 其余格子是**身体**，飞行时身体只沿自己的折线依次前进，**不会横向扫过旁边的格子**。

### 2.2 关卡

```python
{
    "id": 9, "name": "第9关 大盘如月", "shape": "round",
    "mistakes": 3, "rows": 21, "cols": 21,
    "seed": 9909072, "time_limit": 460,
    "arrows": [ ... ],
    "solution": [37, 36, ..., 0],   # 一条已验证的通关顺序
}
```

`shape` 是造型名，交给 `game/shapes.py` 展开成遮罩格子集合；线段只会铺在遮罩内，
底部的辅助线点阵也只画在遮罩格上 —— 这一条就让整个棋盘呈现「圆」「心」等造型，
和参考录屏里的关卡构图一致。

字母玩法的关卡多两个字段：`"shape": "letter"` 与 `"letter": "M"`，遮罩由
`game/letters.py` 的点阵字模栅格化而来（第 9 章）：

```python
{
    "id": "M", "letter": "M", "shape": "letter",
    "mistakes": 3, "rows": 23, "cols": 17, "time_limit": 300,
    "arrows": [ ... ], "solution": [ ... ],
}
```

取遮罩统一走 `shapes.level_cells(level)`，形状关卡与字母关卡都从这一个口子进出。

### 2.3 棋盘 Board

- `_occ[rows][cols]`：每格属于哪一支箭，空格为 `None`；
- `arrows`：还留在盘上的箭；
- `wrong_ids`：点错过的箭，界面把它涂成暗红并常驻显示；
- `_history`：撤销栈，每次出手前压一份快照（活着的箭 id 列表 + 红心数 + 错标集合）。

## 3. 核心规则：射线检测

线段箭沿自身折线滑出时，身体只经过自己原来的格子，所以「能不能飞出去」只取决于
**箭头端朝向上有没有别的线段**：

```text
函数 can_fly_arrow(arrow):
    (dr, dc) = 方向增量(U:-1,0 / D:1,0 / L:0,-1 / R:0,1)
    (r, c) = arrow.head + (dr, dc)
    当 (r, c) 仍在棋盘内时循环:
        若 _occ[r][c] 上有别的箭: 返回 False（被挡住）
        (r, c) += (dr, dc)
    出界都没遇到别的箭: 返回 True
```

这正是参考游戏的判定方式：被挡时线段会朝箭头方向冲一下再弹回，扣一颗红心，
并且那支箭在此后一直保持暗红标记，方便玩家记住「这条路走不通」。

## 4. 关卡生成：逆向构造法

手摆关卡几乎不可能保证「必然可通关」，所以关卡全部由算法生成。

**正向规则**：若线段 B 挡在 A 的箭头射线上，则 B 必须先于 A 被清除。
直接按这个规则正向搜索很难构造出又满又可解的盘面，于是反过来做：

1. 从空棋盘开始，一支一支把箭「放」回去，**放箭顺序 = 通关顺序的倒序**；
2. 放第 k 支箭时只要求一件事：**它自己的箭头射线上没有已经放好的箭**；
3. 这一条恰好等价于「按放置顺序倒着点，每一步的射线都是空的」——第 k 支箭飞的
   时候，留在盘上的正是比它早放的那 k-1 支，而它在放置那一刻就确认过躲开了
   这些箭，所以关卡必然可通关；
4. 落点用「代价优先 + 小窗口随机」，兼顾**铺得满**与**每局不一样**；
5. 单支箭的身体从箭头端往回生长，`straight_bias` 只有 0.24 —— 也就是每一步
   七成以上概率拐弯，于是长箭也不会变成一根长横条，而是绕来绕去的折线。

### 4.1 阻挡是设计目标，不是副产品

早期版本在放置时还加了第二条约束：**箭的身体也不许落在已放好箭的射线上**。
它看起来像是在「预留空走廊」，实际上和第一条合起来等价于

```text
射线(a) ∩ 身体(b) = ∅          （对任意两支箭 a、b）
```

也就是每支箭的出口走廊永远是空的：开局全盘任何一支都能直接飞出去，
**点什么都对，关卡退化成「无脑乱点必通关」**。这条约束对可通关性毫无贡献，
纯属把玩法抹掉，已经删除。

删掉之后，**后放的箭（先点）可以名正言顺地站在先放的箭（后点）的射线上**，
这就是盘面上的阻挡与先后依赖 —— 也正是参考录屏里的样子：箭头常常直接顶在
别的线段上。

难度由一个旋钮控制：`ray_pref` —— 挑落点时偏好「箭头前方空走廊长」还是
「短」。走廊越长，越容易被后面放的箭压住，阻挡就越多。实测：

| `ray_pref` | 开局能直接飞的比例 | 被挡箭比例 | 填充率 |
|---|---|---|---|
| 0.0 | 99% | 0.9% | 0.924 |
| 0.5 | 57% | 43% | 0.950 |
| 1.0 | 22% | 78% | 0.965 |

注意填充率是**跟着一起涨**的：走廊长意味着那些格子会被后面放的箭填满，
「铺得满」与「有阻挡」并不矛盾，反而互相成全。

### 4.2 关键参数

参数都在 `game/generator.py` 的 `DEFAULT_STYLE`：

| 参数 | 值 | 作用 |
|---|---|---|
| `max_piece` | 26 | 单支箭最长格数 |
| `straight_bias` | 0.24 | 继续直行的概率，越小拐弯越密 |
| `stop_chance` | 0.03 | 提前收尾的概率 |
| `window` | 4 | 在「最省的 N 个候选」里随机挑，控制贪心程度 |
| `ray_pref` | 0.65 | 偏好长走廊的程度，越大阻挡越多 |

`tools/generate_levels.py` 给每一关单独配 `ray_pref` 与「开局可飞上限」，
每关重启 240 次，在满足上限的候选里取填充率最高的一版。当前 12 关：

| 关卡 | 形状 | 棋盘 | 箭数 | 填充率 | 开局可飞 | 被挡 | 平均挡者 |
|---|---|---|---|---|---|---|---|
| 第1关 | 矩形 | 17×13 | 21 | 0.941 | 13 (62%) | 38% | 0.76 |
| 第2关 | 矩形 | 18×14 | 29 | 0.929 | 14 (48%) | 52% | 2.17 |
| 第3关 | 圆形 | 16×16 | 28 | 0.962 | 13 (46%) | 54% | 1.07 |
| 第4关 | 菱形 | 18×18 | 25 | 0.933 | 11 (44%) | 56% | 1.96 |
| 第5关 | 十字 | 18×18 | 17 | 0.968 | 7 (41%) | 59% | 1.94 |
| 第6关 | 心形 | 18×18 | 25 | 0.956 | 9 (36%) | 64% | 1.20 |
| 第7关 | 矩形 | 21×15 | 33 | 0.937 | 8 (24%) | 76% | 2.67 |
| 第8关 | 三角 | 17×18 | 19 | 0.963 | 4 (21%) | 79% | 2.21 |
| 第9关 | 圆形 | 21×21 | 38 | 0.943 | 6 (16%) | 84% | 2.84 |
| 第10关 | 沙漏 | 20×17 | 23 | 0.928 | 3 (13%) | 87% | 1.96 |
| 第11关 | 圆环 | 21×21 | 35 | 0.931 | 4 (11%) | 89% | 2.31 |
| 第12关 | 矩形 | 25×19 | 55 | 0.931 | 6 (11%) | 89% | 4.22 |
| **平均** | | | 29.0 | 0.943 | 31% | 69% | 2.11 |

「开局可飞」逐关递减且**严格不回升**：第 1 关六成多能直接点（给新手留容错），
第 12 关只剩一成（55 支箭里开局只有 6 支能点，其余全被压住）。

怎么保证「严格不回升」？只靠 PLAN 里那张上限表是压不住的 —— 每一关都在自己的
上限内独立挑最满的一版，实际值可能比上一关还高（上限 0.78 拿到 0.62，下一关上限
0.65 却拿到 0.64）。所以 `build_one()` 做了两件事：

1. 把上限压到「上一关**实际**值 − `FREE_MARGIN`(0.004)」以下；
2. 上限压下去以后，**同一个种子不一定够得到**（环形 21×21 用原种子只能到 14.6%，
   换种子能到 10.8%），而且够到了也可能铺得很稀 —— 于是上限没满足、或满足了但
   填充率不到 `GOOD_FILL`(0.92)，就换个种子再来一遍，取「满足上限里铺得最满」的一版。

校验里也加了这条：`--check` 会打印整条难度曲线，出现回升就报 BAD。

生成后要过两道独立检查：`verify_solution()` 拿真正的 `Board` 按 `solution`
模拟点一遍，`solver.solve()` 再独立解一遍，两边都过才写进 `game/level.py`。

## 5. 可解性与 AI 求解：拓扑排序

一支箭能不能飞只取决于箭头射线上有没有别的箭；飞出去只是把自己从盘上拿掉，
不会动别人。所以可以定义一个有向关系 `a 挡 b`，整个问题退化成拓扑排序：

- 图**无环** → 任意一个拓扑序都是一条通关顺序；
- 图**有环**（两支箭互相封死）→ 环里谁都不能先走，必然无解。

`game/solver.py` 用 Kahn 算法跑一遍，O(n²)，最大的关卡 25 支箭也是毫秒级。

这里曾经写的是「深度优先搜索 + 失败局面记忆化」。在**无阻挡**的盘面上它看着
挺好用 —— 但那是假象：每步平均四五支可飞、深度一二十层，搜索树指数爆炸，
60 万节点的上限瞬间打满，于是**明明有解的关卡被报成无解**，提示与 AI 自动求解
全部失效（而当时的测试恰好只跑在无阻挡的关卡上，所以一直没暴露）。
换成拓扑排序后，正确性和速度都变成确定的。

### 6.1 窗口尺寸：逻辑画布 + 等比缩放

画面永远渲染在固定的逻辑画布 `640 x 1140` 上，`_present()` 再按
`view_scale` 等比缩放贴到窗口中央，`_to_world()` 把鼠标坐标反算回画布坐标
（缩放后点击依然精准，`tests/test_window.py` 有覆盖）。因此窗口怎么拖都不影响
布局，改变的只是整体缩放系数。

这里踩过一个真实的坑：**窗口默认高 1000，比桌面还高**。进程不是 DPI 感知的，
在缩放 200% 的屏幕上 pygame 看到的桌面只有 `1440 x 900`，而 Windows 会把高过
桌面的窗口垂直居中 —— 结果标题栏跑到屏幕上方之外（`top = -81`）、底边跑到
屏幕下方之外（`bottom = 958`），**用户既抓不到边框去缩放，也抓不到标题栏去拖动**。

现在的做法是 `main.desktop_size()` + `fit_to_screen()`：启动时按桌面尺寸减去
`SCREEN_RESERVE_*` 余量再等比收敛，最小尺寸也一起收敛，保证上下边框都在屏幕内。
另外 `_resize()` 不再无脑调 `set_mode()` —— SDL2 在窗口尺寸变化时本来就会自动换掉
display surface，拖拽过程中反复重建窗口会卡顿、还可能打断 Windows 的模态拖拽
循环；只有尺寸和当前 surface 对不上（比如 dummy 驱动）时才补一次。

### 6.2 棋盘缩放与平移：拖得动，且不会把点击吃掉

底栏滑杆把格子在 `ZOOM_MIN(0.65)` ~ `ZOOM_MAX(1.35)` 之间放大缩小。缩放本身只需
重算格子边长，问题是**放大以后棋盘会溢出可视区**：12 关在最大缩放下无一例外横向
溢出 131~171 像素（其中 5 关纵向也溢出 158~252 像素），溢出部分既看不到也够不着。
所以棋盘几何里多了一个平移量 `self.pan`，几何计算拆成三层：

| 层 | 函数 | 职责 |
|---|---|---|
| 可用区 | `_viewport()` | 顶栏与底栏之间那条 `640 x 874` 的区域，棋盘只能活动在这里面 |
| 零平移基准 | `_base_position()` | 放得下就居中、放不下也居中，作为 `pan` 的参照原点 |
| 夹取 | `_clamp_position()` | 放得下 → 锁死在居中的位置；放不下 → 允许拖到棋盘边缘与可视区边缘对齐为止 |

夹取后的结果会立刻写回 `pan`（而不是留着原始累加值），否则拖到边界再往回拖时，
指针要先「空转」掉之前多拖的那一段，手感像粘住了。

**拖动与点击的冲突**是这块最麻烦的地方。正式关卡填充率 0.94~1.00，几乎每一格都是
线段，如果「按下即点」，那想拖棋盘就一定会先点飞一支箭（被挡的话还白扣一颗心）。
于是把交互改成**按下记账、抬起了结**：

```
MOUSEBUTTONDOWN(左键) → 记下按下的位置与那一格（不动作）
MOUSEMOTION           → 位移超过 DRAG_THRESHOLD(8 逻辑像素) ⇒ 改判为拖动棋盘，点击作废
MOUSEBUTTONUP(左键)   → 仍是这次点击 ⇒ 执行「飞出 / 被挡」判定
```

中键 / 右键按住可以直接拖（不参与点击判定），滚轮缩放锚在鼠标位置上 ——
`_compute_geometry(anchor)` 会记下锚点在棋盘里的相对位置（0~1），缩放后反解出
新的 `pan`，让指针底下的那个位置尽量不动（不锚定的话，缩放永远是围绕中心做，
想放大看角落就得「放大一下、再拖一下」来回倒）。

棋盘比可视区小的时候拖动是**故意不生效**的（位置锁在正中），拖动只在该有用
（放大到溢出的那 5 个档位以上）时才有反应；换关、重开、缩小到装得下时，
`pan` 都会自动归零，棋盘重新摆回中间。

## 7. 动效

### 7.1 飞出：沿自身折线「流」出去

飞出不是把线段当刚体平移，而是**让整条线的每一节沿自己那条折线往前走**：
第 i 节的位置是折线上弧长 `t + i` 处（`t` 每帧增加 `FLY_SPEED × dt`）。所以画出来的
图形就是「滑出路径上弧长 `[t, t + n - 1]` 的那一段折线」，再加上箭头。

关键在**怎么取这一段**。最直觉的写法是每个节点各取一个采样点：

```python
points = [point_at(route, i + offset) for i in range(n_cells)]   # 错
```

采样点之间隔着整整一格，落在两点之间的拐角就会被这两点连成的**斜弦切掉**：直角被削成
斜角，而且 `offset` 是连续增长的，这个斜角每前进一格就「削平 → 复原」一次（`FLY_SPEED`
下每秒 26 次）—— 看上去就是转弯处一闪一闪地抖。量一下更直观：40 像素的格距下，
被切掉的那一截最多让折线**缩短 23 像素**，并且在 0 到 23 像素之间来回振荡。

`flow_points()` 的做法是把区间内的整数节点补回来，画出来的就是原折线真正的一段：

```python
def flow_points(route, n_cells, offset):
    start, end = offset, offset + n_cells - 1
    points = [point_at(route, start)]
    for index in range(int(start) + 1, int(end) + 1):   # 区间内的节点
        if start < index < end:
            points.append(route[index])
    points.append(point_at(route, end))
    return points
```

这样折线长度恒等于 `(n_cells - 1) × 格距`，与相位无关 —— 这条「长度守恒」也写成了
回归测试（T10）。附带一个好性质：`route` 是四邻接格子连成的，所以每一段都横平竖直。

### 7.2 线段的画法：圆角折线 + 飞镖箭头 + 一圈外描边

整支箭就是一条**粗折线**加末端一个**箭头**，折线横平竖直，所以直段的边本来就是锐利的
整数像素边界 —— 需要抗锯齿的只有曲边和斜边这两处：折线的拐角 / 端头，以及箭头的斜边。

**线宽**取格距的 `SEGMENT_WIDTH_RATIO = 0.30`（`MIN/MAX = 4/15`）。这个数是拿参考录屏的
截图逐像素量出来的：参考图里金黄那支箭实占 14 px，格子间距约 56 px，线宽约为格距的 1/4。

**折线**用 `stroke_polyline()` 逐段画实心矩形，再在**两端与真正拐弯的节点**补圆点
（`joint_indices()` 用叉积判断拐弯）。两个容易踩的细节：

- 直线段上的中间节点**不补**圆点。补了会在线上挂一串小疙瘩，直线看着就不直了；
- 圆点的直径必须**严格等于线宽**。pygame 画宽 `w` 的线时涂的是
  `y_center - (w-1)//2` 到 `y_center + (w-1)//2` 这 `w` 行，注意它**不是**以 `center`
  为中心左右各半个宽 —— 所以圆点贴图要摆到 `stroke_span(center, w)` 上，直径也要取
  `2r` 而不是画整数圆惯用的 `2r+1`。早先按 `2r+1` 做，直径比线宽多出 1 像素，
  每个拐点、每个端头都会鼓出一小块（放大看就是「线上挂了一串疙瘩」）。

**箭头**不是等腰三角，而是一枚**飞镖**：4 个顶点 = 尖端、两枚**前掠**的倒钩、尾根处的
收口点。前掠量 `HEAD_SWEEP_RATIO = 0.42`，后缘因此向内微微兜住线身，线端那个圆头正好
填进凹口里，不会在箭头屁股后面露出一截。尺寸按线宽缩放：底边 `HEAD_SPAN_RATIO = 1.90`、
尾根到尖端 `HEAD_LENGTH_RATIO = 2.15`。

**外描边**：深色底上线段的边缘本来就靠明度差「切」出来，加一圈更深的外描边之后边缘更
利落，两条线挨在一起时也多一层分隔，盘面不至于糊成一片。描边宽 `RIM_RATIO = 0.09`（跟着
线宽走），颜色是**线身色乘一个系数**（`RIM_SHADE`）而不是减一个常数 —— 乘系数色相不变，
减常数会把蓝、紫这类深色直接压成黑，描边就脏了。压暗的力度按主题给：夜间 `0.46`（压狠
一点边缘才切得出来），日间 `0.72`（浅底压狠了整片线段发黑）。

描边**不是**「把整支箭放大」：那样箭头会比线身多粗出好几倍。实现是拿同一套绘制函数画两
遍 —— 先画「线身加宽 `2×rim`、箭头往外撑 `rim`」的描边色，再画正常尺寸的线身，两边才是
同样厚的一圈（`draw_segment(..., outline=True)`）。

圆点与箭头两张小图都用 **4 倍超采样**画好再缩回来（`disc_sprite` / `arrow_head_sprite`），
边缘因此有半透明的过渡像素。pygame 的 `draw.circle` / `draw.polygon` 都不带抗锯齿，
斜边是一排锯齿，动起来还会「爬行」。这两张小图按「形状 + 尺寸 + 颜色（+ 描边外扩量）」
缓存，画一帧只是几次 `blit`（实测整帧 4.3 ms，60 FPS 的预算里很宽裕）。

盘面静态线段与飞行中的线段共用同一个 `draw_segment()`，所以 `offset = 0` 时两者逐像素
一致，起飞瞬间不会跳；悬停 / 提示的高亮环走 `outline=False`（光晕再描边就脏了）。

### 7.3 其它动效

| 动效 | 实现 |
|---|---|
| 残影 | 尾节离开某个格点后，原地亮起一个灰点，快速淡入再线性淡出（共 `TRAIL_LIFE` 秒） |
| 被挡 | 线段沿自身折线冲出一小段再弹回（`PUSH_STEPS × sin(πt)`），同时涂成暗红并常驻标记 |
| 提示 | 目标线段的描边做呼吸式发亮 |
| 自动求解 | 维护一个待点队列，每 0.30 秒自动点一支，动画期间暂停 |

### 7.4 帧步进上限

主循环的 `dt` 夹在 `MAX_FRAME_DT = 0.05` 秒（`_frame_dt()`）。切窗口回来、系统忙的时候
`clock.tick()` 可能一次返回几百毫秒，飞行线一步就跨过好几格，看起来像「瞬移」了一下；
夹住上限之后，宁可让动画慢半拍，也不会让它跳。

## 8. 界面观感：渐变、柔光、投影、卡片

原来的界面是一块纯色底加一圈硬描边 —— 功能没问题，但画面是「平」的：背景没有层次，
按钮、卡片跟背景糊在一起，按下去除了换个颜色没有任何反馈。第 8 节做的就是把层次拉开。
所有原语都在 `game/paint.py`，配色都从 `theme.py` 取。

### 8.1 为什么单独开一个 `paint.py`

这些效果都是「同样的形状反复画」，而 pygame 里做柔边只能靠**预先画好再贴**。所以统一
走一套「参数 → 预渲染贴图 → 缓存 → blit」的套路：

```python
def _cached(key, build):
    value = _CACHE.get(key)
    if value is None:
        if len(_CACHE) >= _CACHE_LIMIT:      # 上限，防止无节制地灌
            _CACHE.clear()
        value = _CACHE[key] = build()
    return value
```

**key 里包含全部颜色参数**，所以切主题不需要手动清缓存：颜色一变，键就变了，自然
build 出新的一套。代价见「已知限制」——将来若加了跟颜色无关的动态参数（比如随时间
变化的量），必须显式把那个参数塞进 key。

大图（卡片、面板）一律**按 2 倍画再 `smoothscale` 缩回来**：圆角与描边因此自带抗锯齿，
渐变也更顺。缩小时透明处要填成填充色（`body.fill((*fill, 0))`），否则取平均时会把黑
混进边缘 —— 这个坑在做线段圆点时已经踩过一次（见 7.2）。

### 8.2 整页背景：竖向渐变 + 柔雾 + 一团柔光

```python
self.canvas.blit(paint.vertical_gradient(
    (WINDOW_WIDTH, WINDOW_HEIGHT), pal.bg_top, pal.bg_bottom), (0, 0))
paint.blit_fog(self.canvas, size, pal.fog)          # 只有非对局界面铺
paint.blit_glow(self.canvas, center, 430, pal.glow, 62, 2.3)
```

- 渐变先画一条 **1 像素宽的色带**（只算 height 次颜色插值），再横向拉满 —— 逐行 fill
  比逐像素算快得多，横向又完全不需要计算；
- 柔光先在一张 **64×64 的小图**上按 `(1 - d) ** softness` 算衰减，再 `smoothscale` 放大：
  放大本身就把阶梯抹平了，代价只剩 4096 次循环；
- 柔光的中心跟着棋盘中心走（`_view_center()`），视线自然落在盘面上；菜单与开始页则
  固定在画面中上部；
- **柔雾**（`Palette.fog`）是几团错开的低透明度色块 —— 左上靛蓝、右上紫、左下青、
  右下蓝，位置按画布比例给（`0.16 / 0.09` 这样），换分辨率不用重调。它让底子从
  「一条从亮到暗的平涂」变成有远近的雾面。夜间是**提亮**、日间是**压暗**（浅底上
  叠加淡蓝会降低亮度），所以验收断言只看「颜色确实变了」，不假定方向。

**柔雾只在非对局界面铺。** 对局中整屏已经是彩色线段了，再叠一层雾只会压住棋盘的
可读性；而且放大拖动时棋盘会盖住大半个屏幕，雾铺在上面没有任何意义。

**柔雾是预合成的**：每团柔光自己都有缓存贴图，但逐团贴仍是四张 800+ 见方的半透明图
逐帧混合，一页 4 ms 上下。雾不动，于是先合成成一张整屏贴图（`fog_layer`，叠加顺序
不变、结果完全一样），之后每帧只剩一次 blit。

**开始页走的是另一套底**（`pattern_layer`，见 8.9）：底色不再从 `bg_top` 到 `bg_bottom`，
而是换成 `menu_top → menu_bottom`，上面再平铺一层同色调的箭形暗纹 —— 玩家给的参考图
是「一块薄荷青底 + 一层几乎看不见的暗纹」，单靠渐变出不来这种「有纹理但不抢戏」的底子。
日间因此是薄荷青，夜间仍留在原来的深蓝上（只加暗纹，不加亮底）。

### 8.3 栏与棋盘面板：半透明玻璃 + 渐隐阴影

顶栏 / 底栏做成一层**半透明面板**（`alpha≈208`）+ 一条 1 像素分隔线 + 朝盘面那一侧的
渐隐阴影（`edge_fade`，从实色线性衰减到全透明）。好处是棋盘铺到底下时还能透出来一点
（放大拖动时尤其明显），而文字和图标因为有底衬始终有对比度。

棋盘本身垫在一块圆角面板上（比可视区小 16 像素），渐变 + 细描边 + 投影 —— 盘面因此
是「一块台面」，而不是一堆飘在背景上的线段。放大拖动时棋盘可以铺到面板外面去，
这反而强化了「看得见的只是其中一块」的感觉。

### 8.4 卡片与按钮：三段式 + 三态

一张卡片由三段组成，`card_surface()` 一次画齐：

| 段 | 做法 |
|---|---|
| 填充 | 竖向渐变，圆角用一张 `BLEND_RGBA_MULT` 圆角遮罩裁出来 |
| 高光 | 顶部一团柔光（`sheen`），模拟「光从上面打下来」 |
| 描边 | 在裁剪**之后**画，1~3 像素，正好压住边缘 |
| 投影 | 一组同心圆角矩形，越外圈 alpha 越低（`_paint_shadow`），模拟高斯模糊 |

按钮在此基础上多一层**状态**：悬停把渐变提亮 16 并换成强调色描边；按下把渐变压到
0.86、整体下沉 2 像素、同时收起投影 —— 「按下去」这件事有物理感，而不只是换个颜色。

同一屏里的主次按钮用 `kind` 区分，两者的**深浅是反过来的**：

| kind | 底 | 字 | 用在哪 |
|---|---|---|---|
| `primary` | 蓝色渐变实心 | 白字 | 开始页的「基础玩法 / 字母玩法」 |
| `ghost` | **浅色纸片**（`ghost_top/bottom`） | **深字** | 「规则介绍 / 随机关卡」、返回 |

一整列按钮因此是「蓝 / 白 / 蓝 / 白」的节奏，而不是一片同色。夜间那张纸片不是纯白
而是浅蓝白（`236, 241, 253`）：深色底上纯白会亮得晃眼。纸片上的字**不垫投影** ——
深字再叠一层深色投影只会把笔画糊掉，参考图里的白卡也是干净的一行字。

滑杆的轨道做成凹槽（底色压暗 + 上缘暗影），已填充的一段用上下两个圆角矩形做出一点
光泽。**这里刻意不走去缓存的卡片贴图**：拖动时宽度每帧都在变，缓存会被不停灌满然后
整片清空，反倒比直接画两个圆角矩形更费。

### 8.5 顺带调整的几处排版

| 界面 | 调整 |
|---|---|
| 开始页 | 规则说明与进度各装进一张卡片（原来是一堆字飘在空背景上）；按钮整体下移，和进度卡之间留出间距 |
| 选关页 | 卡片加大到 124 并上移；下方补一张「已通关 / 进度条 / 累计星数」的进度卡，填掉原来那片空白 |
| 菜单 | 面板高度按「项数 × 52 + 标题区 + 底部留白」重算 —— 之前 6 项时最后一项正好顶在面板底边上 |
| 结算 | 面板投影压得更重（画面里最高的一层）；标题按结果染色（通关绿 / 失败红 / 全清金），满星额外加一圈金色柔光 |

### 8.6 性能

`tools/perf_bench.py` 量的是「缓存建好之后的稳态」每帧耗时（`_draw` 一次）：

| 界面 | 中位 | 最大 |
|---|---|---|
| 开始页（暗纹底 + 拼装标题 + 吉祥物） | 3.02 ms | 7.51 ms |
| 规则页 | 6.90 ms | 10.07 ms |
| 基础选关 | 4.10 ms | 19.17 ms |
| 字母选关 | 1.91 ms | 4.16 ms |
| 字母关（静态） | 2.77 ms | 6.22 ms |
| 字母关（飞行中） | 2.91 ms | 5.84 ms |
| 第 1 关（静态） | 3.20 ms | 7.04 ms |
| 第 12 关（静态） | 6.96 ms | 12.89 ms |
| 第 12 关（飞行中） | 5.85 ms | 12.10 ms |
| 菜单展开 | 8.01 ms | 10.62 ms |
| 第 12 关（日间） | 6.06 ms | 14.50 ms |

同一台机器上连跑三次，中位数会差 ±0.3 ms 上下（后台负载），表里取的是一次完整运行
的结果，「最大」那一列抖动更明显（如基础选关 19 ms 是单帧毛刺）。

中位都落在 60 FPS 的 16.7 ms 预算内。最贵的是「规则页 / 菜单展开」—— 除了面板本身，
还要整屏铺一层半透明遮罩，页面上又是一堆小卡片。

开始页反而是**最便宜的一档**，因为整块底（渐变 + 暗纹）被预合成成了一张不透明贴图，
一帧只剩一次 blit；拼装标题的五片、吉祥物也都各自是一张贴图。整页的构建成本全在
第一次画时付：缓存全冷的首帧约 150 ms（标题 5 片 + 吉祥物 28 ms + 底纹 4 ms），
之后切主题才会再付一次 —— 切主题时颜色全变、缓存整体失效。

一处需要留意的：

- **规则页正文多折了几行**（3 行长句 → 6 行短句），文字是每帧现 `font.render` 的，
  多出约 1 ms 的光栅化。真要继续压，得给文字也加一层缓存 —— 目前没必要。

**踩过的两个性能坑都出在「逐帧混合半透明大图」上**：柔雾四团让开始页从 2.90 涨到
4.15 ms，暗纹整屏逐块贴也会掉帧。两次的解法是同一个 —— **把这些不动的图层预合成成
一张贴图**（`fog_layer` / `pattern_layer`），每帧只留一次 blit。暗纹若不预合成，光
平铺就是上百次小 blit 外加整屏透明混合。

棋盘加密到约 1.4 倍之后，最贵的一档从 3.32 ms 涨到 6.78 ms（第 12 关静态）——
格子多了约九成，铺底色、描边、箭头都得按格子走一遍。仍然只有预算的三分之一。

### 8.7 艺术字：先放大、再加工、最后缩回

开始页的标题「一箭又一箭」要的是「游戏 logo」的观感 —— 只是换个字体颜色不够，
得有渐变、描边、高光、投影四层。`paint.art_text()` 的做法：

1. `font.render(text)` 拿到一张**抗锯齿的白字**（alpha 就是形状）；
2. 把它 `smoothscale` 放大 `ART_SUPERSAMPLE = 3` 倍；
3. 在放大空间里做加工：
   - **描边**：把白字染成描边色，按「半径 r 内所有整数偏移点」（一个圆盘）逐点
     `BLEND_RGBA_MAX` 铺一遍。**用圆盘而不是 4 / 8 个方向**是关键 —— 只铺 8 个
     方向时，斜笔的描边会被啃出缺口；
   - **渐变主体**：拿 `vertical_gradient` 与字的 alpha 相乘（`BLEND_RGBA_MULT`）；
   - **顶部高光**：再叠一层「上实下透明」的 `edge_fade`，同样乘字的 alpha；
   - **投影**：把描边形状整体挪 `(0, dy)`，垫在最底层；
4. `smoothscale` 缩回原尺寸 —— 放大空间里的那点锯齿一并被平均掉。

留白 `pad = 内描边 + 外描边 + 2 + max(|dx|, |dy|) + |lift|` 对上下左右一致，
所以返回的 surface **中心就是文字中心**，调用方直接 `get_rect(center=...)` 摆位。
整套结果按「字体 + 文字 + 全部颜色 + 各宽度 + 偏移」缓存，切主题会自动换一套。

#### 8.7.1 卡通贴纸配方：三层颜色 + 字脸上浮

玩家给了一张参考截图，要的是那种「贴纸」标题。和早期金色渐变的版本比，
多两样东西：

- **第二圈描边**（`outline2` / `outline2_width`）。参考图是「奶白字面 + 近黑内边 +
  浅色外边」的三层结构。外圈先按 `outline_width + outline2_width` 铺一个大圆盘，
  内圈再按 `outline_width` 盖上去，于是只看得见 `outline2_width` 那一圈。
  三层颜色互相形成对比，所以这套配方在深色底（夜间）和浅色底（日间）上都读得清 ——
  日间把外圈换成奶黄，免得白色外圈在浅底上化掉。
- **`lift`：描边整体下移、字面不动**，底部那圈边就比顶部厚，字看起来是浮在边上的。
  这是贴纸感的来源；平描边（`lift=0`）看着像印上去的。

#### 8.7.2 拼装式标题：横条 + 逐字换色

参考图里两个「一」不是汉字，而是红 / 蓝的圆头横杠，最后一个「箭」还换了绿色。
所以标题不再是「一段文字」，而是五片拼起来的：`paint.art_banner()` 把
`art_text`（字符）与 `art_bar`（胶囊横条）横着排。

- `art_bar` 复用同一套渲染栈（超采样 + 双层描边 + 竖向渐变 + 顶部高光），
  连 `pad` 的算法都和 `art_text` 逐项对齐 —— 两者高度天然相等。
- 拼接时**横向按墨迹边界（`get_bounding_rect`）排布**。每片四周都留着描边用的
  透明边距（本例约 22 px），如果直接按 surface 宽度累加，两片之间会凭空多出
  44 px 的空隙，字就散开了。

#### 8.7.3 两个性能坑

- **描边宽度曾经是「超采样像素」**，而 `pad` 是「原始像素」—— 单位不一致，于是
  标称 6 px 的描边实际只有 2 px，外圈更是细到缩回后被平均成灰色。现在统一成
  原始像素，进 `stamp` 前乘 `ART_SUPERSAMPLE`。
- 单位统一后描边圆盘半径变成 18（超采样像素），**逐点 blit 一次要 42 ms**。
  改法是在 1/`EDGE_DOWN`(=2) 分辨率上做膨胀：偏移点数与单点面积各降到 1/4，
  总开销约 1/16，再放大回来时边缘被插值柔化，对一层纯色描边反而更像抗锯齿。
  整页首帧从 210 ms 降到 **62 ms**，稳态 3.1 ms。

### 8.8 文字排版：按宽度折行

规则页的说明文字原来是**写死一行**的：

```python
rules = ["点击彩色线段，它会沿着自己的轨迹滑出、再从箭头方向飞出", ...]
for index, line in enumerate(rules):
    self._draw_text(line, self.font_normal, pal.text_dim,
                    topleft=(how.left + 26, how.top + 70 + index * 42))
```

26 个字 × 23 px = 598 px，而卡片内宽只有 540 px —— 句子直接画到卡片外面去。
**这种溢出不会报错、不会抛异常**，测试也照样过，只能靠肉眼发现（玩家就是这么发现的）。
同类问题还有两处：卡片高度是写死的数字，文案一长就顶出底边；按键功能表「缩放棋盘
（也可用 - 与 =）」在右列也超出了 8 px。

现在的做法是**按内容排版**，`paint.wrap_text()` 负责折行：

1. **切单元**（`_word_tokens`）：连续的 ASCII 算一个单元（`第 12 关` 不会折成 `第 1`
   和 `2 关`），一对全角括号连同内容也算一个（`（也可用 - 与 =）` 整段挪到下一行，
   不会断在「（也」中间），其余逐字；
2. **贪心折行**：一行里尽量多塞，塞不下就断；
3. **均衡**（`balance=True`）：中文句子常常只比容器宽一点点，纯贪心会折出「满满一行 +
   两三个字的尾巴」。做法是**二分一个更窄的有效宽度**，取「仍折得出同样行数」的最小值
   —— 行数没变，余量却均摊到每一行。`26 字 / 540 px` 于是变成 `13 + 13` 而不是
   `24 + 2`；
4. **避头尾**：落在行首的收尾标点退回上一行末尾（中文允许逐字断行，但标点跟着下一个
   字跑到行首很脏）。

版面则是**按内容累加**：`_compute_rules_layout()` 先折行拿到正文行数，据此算「怎么玩」
的高度，下一块面板接在它下面，依此类推。结果算一次缓存起来（每帧重算意味着几百次
`font.size` 度量）。现在往 `HOW_TO_PLAY` 里再加一句话，版面会自己长高，不会溢出。

回归测试量的是**文字的实际渲染宽度**（`font.size(line)[0] <= 卡片内宽`），而不是
「有没有调用过折行函数」—— 后者只能证明代码被走到了，前者才对应「没有画出界」。

### 8.9 开始页：暗纹底 + 卡通箭吉祥物

玩家给的参考图里有两样东西是原来没有的：**一层同色暗纹的底**，和**标题下方那只带脸
的卡通箭**。参考图的配色其实就是本项目的日间那套（逐像素采样对得上：按钮蓝
`117,166,243 → 89,140,228`、文字 `42,46,70`、进度条 `38,176,164`），所以方向定成
「同一套结构，日间换成参考图的薄荷青，夜间留在深蓝上」。

#### 8.9.1 底纹：用游戏自己那支箭铺壁纸

`paint.pattern_layer()` 把底色渐变和暗纹画成**一张不透明贴图**，每帧只 blit 一次。
图案不是照抄参考图的圆角方块，而是**用游戏自己那支胖箭**（`_arrow_shape`，和盘面上
那支同一个函数），隔行错开半格、奇偶格上下翻转 —— 铺出来像壁纸，又和玩法点题。

几个要点：

- 暗纹的对比度必须**极低**：日间 `pattern_alpha=62`（同色系压深），夜间 `26`（提亮）。
  再浓一点就开始和标题抢注意力；
- 图案本身先按 `s=2` 画再缩回（沿用 8.7 的「先放大、再加工、最后缩回」），缩回时
  顺手把斜边抗锯齿了；
- 结果按「尺寸 + 四个颜色 + 透明度 + 格距」缓存，切主题自动换一套。

#### 8.9.2 卡通箭：四层结构 + 一张脸

`paint.arrow_mascot()` 是纯几何拼的，不依赖任何图片资源：

1. **投影**：三四圈逐渐收窄、逐渐加深的剪影，错开 `(4, 10)` 贴上去，模拟模糊；
2. **外描边**：把剪影按 `grow=描边宽` **再画一遍**填深色（描边不做逐点膨胀）；
3. **箭身**：剪影 × 竖向渐变；
4. **贴边暗面**：剪影 **减去**「往左上挪几像素的剪影」（`BLEND_RGBA_SUB`），得到
   贴着描边的右下那一圈，填暗色压上去 —— 参考图里那股立体感就来自这一圈；
5. **高光块 + 四角星**：亮色块与剪影求交（`BLEND_RGBA_MIN`）；
6. **脸**：眼白 + 瞳孔 + 高光点 + 两道眉毛 + 一道笑，最后整体 `rotate` + 缩回。

#### 8.9.3 三个坑，每个都只表现为「画出来的东西不对」

**圆角不能靠「在顶点画圆」。** 原来箭头的三个圆角是在三个顶点各画一个圆，圆会鼓到
边的**外侧**去 —— 一个锐角三角形画出来像一根骨头。正确做法（`_round_polygon`）：每个
顶点沿**角平分线**内缩 `d = r / tan(θ/2)` 得到两个切点，圆心落在距两边都是 `r` 的地方，
先填「切点围成的多边形」再在三个角补圆。切点还要按绕行顺序连（每个顶点先出边、后进
边），顺序错了会连成蝴蝶结。顺带：描边用的「整体胖一圈」是把每个顶点沿外向角平分线
挪 `grow / sin(θ/2)`，尖角会按比例往外伸长 —— 直接缩放做不到这一点。

**渐变只铺在「箭身框」内，会让箭尾被烧黑。** 箭尾的圆头伸到体框左边，那一块没被渐变
乘到（`BLEND_RGBA_MULT` 乘零 → 全透明），底下的深色描边就露出来了。渐变要铺满整张
画布：框内保持原来的斜坡，框外向上取最亮、向下取最深。这个 bug 只在箭尾呈现，很容易
被当成「设计如此」。

**五官必须单独成层再用剪影裁一刀。** 直接把眼睛画在画布上，位置一偏就浮在箭身外面
（斜着看尤其明显）。做法是把五官画在独立图层上，再用箭身剪影做一次 `BLEND_RGBA_MULT`
—— 剪影是纯白全不透明，乘上去只影响 alpha，等于「按剪影裁剪」。

#### 8.9.4 按钮配色：描边比填充更深

参考图的按钮是「亮蓝填充 + **比填充更深**的描边」，卡通感就来自这一圈深边。原先的
按钮是「填充 + 更亮的描边」（玻璃质感），两套观感完全不同。现在改为：

| 主题 | 填充 | 描边 | 次按钮 |
|---|---|---|---|
| 日间 | `(78,158,232) → (56,134,214)` | `(42,98,182)` | 白纸片 + 深字 |
| 夜间 | `(122,172,250) → (78,124,222)` | `(46,92,182)` | 浅蓝白纸片 + 深字 |

两条随之成立的约束写进了测试：`max(btn_line) < max(btn_top)`（描边更深），
以及夜间的按钮**比日间更亮**（夜间底子暗，按钮不能糊进背景）。

#### 8.9.5 排版：吉祥物插进来，整页节奏要重算

吉祥物的 `width` 是**旋转前**的箭身宽，倾斜 10° 之后包围盒会膨胀约 28%，排位置必须
按画出来的尺寸算。整页因此重排过一次：标题 `y=168`、副标题 `246`、吉祥物中心 `386`
（`width=285` 实测画成 341 × 186，占 293 ~ 479）、四个入口 `552 / 642 / 732 / 822`
（按钮从 84 压到 80 高，间距 90）、进度卡 `880 ~ 1056`、两行底部提示不动。回归测试
逐条断言「副标题底 < 吉祥物顶」、「吉祥物底 < 第一个按钮顶」、「按钮之间 ≥ 8 px」、
「进度卡在最后一个按钮之下」。

## 9. 字母玩法：字模 → 遮罩 → 关卡

基础玩法的 12 关铺在「形状」里（圆、心、菱形……），字母玩法的 26 关则**整盘铺成
一个字母**。这条链路上没有任何新算法，全部复用第 4 章的逆向构造法 —— 只多了一个
「字母遮罩」。

### 9.1 字模与栅格化

`game/letters.py` 里是一套手写的 5×7 点阵字模（26 个字母，每个 7 行 5 列的
`#` / `.` 字符串）。栅格化就是把每个笔画像素摊成 `scale × scale` 的方块，
四周再留一圈空边：

```python
def letter_cells(rows, cols, letter, scale=3, margin=1):
    cells = set()
    for (r, c) in on_pixels(letter):          # 字模里的 '#' 像素
        for dr in range(scale):
            for dc in range(scale):
                cells.add((margin + r * scale + dr, margin + c * scale + dc))
    return cells
```

`scale=3, margin=1` 时棋盘恰好是 **23 × 17**（391 格），26 关尺寸统一 —— 于是
`main._cell_rect` 的几何、选关页的网格都能共用一套。默认缩放下格子边长约 30 px，
比早期 `scale=2`（16 × 12，格子 44 px）密了一档，字母的弧线与斜笔也平滑得多。

**踩过的坑**：`board_size()` 一开始返回 `(列, 行)`，而调用方全都按 `(行, 列)`
解包。字模右下角被裁掉一块、遮罩变成不连通，`build_level` 直接返回 `None`，
表现是「C / G / J / U / V 五个字母生成失败」。这类「两个相邻的 int 谁在前」
的错误编译器不会拦，现在有一个专门的用例钉死它（`test_board_size_is_rows_then_cols`）。

### 9.2 斜笔字母为什么按八连通判定

点阵里 `C`（上横与左竖）、`S`、`J`、`Q` 的笔画是**对角相接**的：

```text
C 的字模          放大后（3 倍）
.###.            ......####....      斜角处两个方块共享一个角点，
#...#            ..####......##      看着是一笔连下来的
#....            ..##..........
```

所以：

- 判定连通性用 `is_connected(cells, diagonal=True)`（八连通），比四连通宽松一档，
  但足以排除「一撮孤零零的碎格」；
- 生成器**不需要改**：它只要求在四邻域内能长身体，对角相接的两个「岛」各自
  独立放箭，飞出去时互不干扰 —— 视觉上仍是一个完整的字母。

### 9.3 26 关的难度曲线

字母关不走「闯关解锁」，26 个字母全部开放；难度靠一条线性爬升的旋钮控制
（`tools/generate_letters.py` 的 `plan_for`）：

| 旋钮 | A | → | Z | 作用 |
|---|---|---|---|---|
| `ray_pref` | 0.45 | → | 0.90 | 越偏好「前方空走廊长」的落点，越容易被后面放的箭压住 |
| `max_free` | 0.58 | → | 0.30 | 开局能直接飞的箭数占比上限 |

实测（26 关平均 20.7 支箭、棋盘 23 × 17、填充率 0.977）：A–E 一带开局 51% 的箭
能直接点，V–Z 一带只剩 29%；被挡比例从 49% 升到 71%。另有 `max_piece` 一条：
字母的笔画窄（`scale=3` 时只有 3 格宽），默认的 26 格会让一支箭一口吞掉整条笔画
（早期 L 关曾经只剩 3 支箭），压到 20 之后箭数才够看。

### 9.4 五个入口与状态机

开始页原来只有「开始游戏 / 关卡选择」，现在换成五个平级入口：

| 入口 | 目标状态 | 说明 |
|---|---|---|
| 规则介绍 | `RULES` | 玩法 + 按键功能表 + 四种玩法；返回时回到进来的那一屏 |
| 入门玩法 | `TUTORIAL_SELECT` | 3 关单格箭，全部开放（T20 之前是直接开第 1 关，没有选关页） |
| 基础玩法 | `BASIC_SELECT` | 12 关，逐关解锁 |
| 字母玩法 | `LETTER_SELECT` | 26 个字母，全部开放 |
| 随机关卡 | 直接 `PLAYING` | 现场生成，不进选关页、不写存档 |

「当前在玩哪一套关卡」用一个 `self.track`（`"basic"` / `"letter"` / `"tutorial"`）
+ `self.levels` 指向对应的那份列表来表达。这样第 4 章那套
「`current_level is levels[level_index]` 才算主线关卡」的存档判断原样可用：
随机关卡不在任何列表里，自然不会写进存档；字母关的 id 是字符串 `"A"`~`"Z"`、
入门关是 `"T1"`~`"T3"`，和基础关卡的 `1`~`12` 在同一个 `cleared` 列表里也不会撞。

**存档 id 和界面关号是两件事**：入门三关的 id 必须是 `T1/T2/T3` 而不是 `1/2/3`
（后者会和基础关撞车，清掉基础第 1 关会顺手把入门第 1 关也标成已通关），但玩家
看到的关号要按顺序是 1/2/3。所以显示的关号统一走 `Game._level_display_number(index)`：
入门线按列表下标返回 `index + 1`，其余玩法沿用 id。T20 之前直接拿 id 当关号，
界面上就显示成了 101/102/103。

**按键表是数据，不是散落的字符串**：`main.KEY_HINTS` 是一个两列的元组，
界面照它画、测试照它断言（包括「不再有 N 键」这条回归）。随机关卡从按键
挪到入口按钮之后，`K_n` 的绑定被删掉，`_handle_key` 里不再有它。
